# CLAUDE.md — apps/fe

Web app (Next.js App Router + NEAR Connect). Owner: Ancung. Design comes from Nabil (#10). Issues: #9, #13–#21.

**Update this file in the same PR whenever you change setup, commands, env vars, dependencies, routes, or FE conventions.** Root rules in `/CLAUDE.md` also apply.

## Stack

- Scaffold with `npx create-near-app@latest fe --frontend next-app --install` in a temporary folder, then move the files here (create-near-app refuses non-empty folders). The `near-dapp` agent skill still mentions removed options (`--contract ts`, `next-page`); follow the create-near-app README. Then delete the generated `package-lock.json` and run `bun install` (the repo uses Bun, see the root `CLAUDE.md`).
- Wallet: `@hot-labs/near-connect` 0.12.0 + `near-connect-hooks` 1.1.6, testnet. **Meteor Wallet is the primary wallet:** show it first and test every flow with it. Per the official manifest (`hot-dao/near-selector`, checked 2 Nov) it supports `signMessage`, `signAndSendTransaction(s)`, `signDelegateActions`, and testnet. Keep other wallets selectable for judges.
- Live view (Mind Graph): our own drawing on a plain `<canvas>` with a small force layout written here (`src/modules/graph`), not `react-force-graph-2d` and no other library (Ancung, 10 Nov: Axel wanted it like Obsidian's graph view; the 6 Nov plan was a fixed SVG map). Visual Builder (bonus): `@xyflow/react` 12.12.1.
- Data and state: `@tanstack/react-query` 5.106.1 for all server data (cache, polling, refresh after approve or freeze). **No global state library.** The current Mind's id lives in the URL (`/minds/[mindId]/…`), every screen reads the Mind through the same React Query hook (one fetch, shared cache), and the last used Mind is kept in `localStorage`. One React context holds the chat run in progress so the chat, the live view and the Approvals badge read the same events. Add `zustand` only if that context gets heavy.
- Streams: chat, approve/decline and builder runs are POST + SSE, so `EventSource` can't be used; read the `fetch` body with `eventsource-parser` 4.1.3.
- Forms: `react-hook-form` 7.91.0 + `zod` 4.6.7 + `@hookform/resolvers` 7.0.3 (validate as you type, as in the design).
- Bottom drawers on phones (`ResponsiveDialog`, "Add a block", a Builder block's settings, the live view) share one roomy spacing (Ancung, 11 Nov, after Welcome). `DrawerContent`'s classes go on the outer popup while its children sit in an inner element with no gap, so the spacing between parts lives on a wrapper inside it (`ResponsiveDialog`) or as margins ("Add a block"); a header there is left-aligned (the drawer centres it by default), except Welcome (`centered`). The sizes: 20 px sides, 20 px between parts, 8 px between a title and its text, 12 px between stacked buttons, and at least 24 px at the bottom (more with a home indicator).
- Toasts: `sonner` 2.0.8 (shadcn's). Theme: `next-themes` 0.4.6 (System, Light, Dark from the account menu). Mind replies: `react-markdown` 10.1.0 with `remark-gfm` 4.0.1 (tables, strikethrough, task lists, bare links; added 9 Nov when a reply's table showed as pipes). Wide tables scroll sideways inside the reply. Springs (Penny is ready, freeze, Builder drag): `motion` 14.10.0; everything else is CSS. Thinking indicators (Thinking... and every running step row, by kind of work: `orb` in `TOOLS` (`runs/data/tools.ts`, every tool's words in one list), read by `stepOrb`, reading searching, websites connecting, writing composing, acting working, time and sums solving, memory breathing, waiting for the owner listening): `thinking-orbs` 0.3.2 (MIT, no runtime dependencies; Axel's pick, 10 Nov): `<ThinkingOrb state size={20|64} />`, a dotted canvas orb that follows the `dark` class, freezes with reduced motion and pauses off screen by itself. Only the free states and the 20 and 64 sizes (libraries.dev marks some as Pro).
- Tests: `vitest` 5.1.0 (unit, `tests/*.test.ts`, config `vitest.config.mts`) with a 15 s test timeout (a few tests that import inside themselves timed out at 5 s on Windows beside the dev server), `@playwright/test` 1.65.0 (flows).
- Motion: easing tokens are in `src/styles/globals.css` (`ease-out`, `ease-in-out`, `ease-drawer` utilities; Tailwind only emits them once used). Rules, durations and chat streaming: `design/CLAUDE.md` "Motion (v0.3)". shadcn components keep their own animation classes; set menus and popovers to grow from `--transform-origin` (Base UI provides it) and make exits faster than entries.
- Scaffolded with `create-near-app` 10.0.0 (`--frontend next-app`). All versions in `package.json` are pinned exactly; do not upgrade during the hackathon.
- `near-connect-hooks` 1.1.6 itself depends on `@hot-labs/near-connect` ^0.11.1, so `package.json` has `"overrides": { "@hot-labs/near-connect": "0.12.0" }` to keep one copy at 0.12.0 (0.12.0 only adds gas-key APIs; checked against the 0.11.4 type definitions). After changing it, delete `node_modules` and run `bun install` so no nested 0.11.x copy is left.
- Wallet order: on testnet the official manifest filters out HOT (no testnet support), so Meteor is already first in the NEAR Connect popup; no reordering code needed (checked 3 Nov).
- UI: Tailwind CSS 4 + shadcn/ui (`base-nova` style, `components.json`, CLI 4.23.0). Add components with `bunx shadcn@4.23.0 add <name>`; they land in `src/components/ui`. Fonts: Geist (`--font-geist-sans`) and Geist Mono (`--font-geist-mono`, wallet addresses only) via `next/font`; the theme maps `font-sans` / `font-mono` to them (named differently on purpose: `--font-sans: var(--font-sans)` refers to itself and can drop the font).
- Primitives in `src/components/ui` are shadcn's, restyled to the design's components (`design/hellonear.pen`, Atomic Components): `Button` variants `default` (primary), `secondary`/`outline`, `brand` (lime, sparingly), `destructive` (`danger-fill`), `ghost`, `link`; sizes `default` (44 px pill), `sm` (36), `icon` (40 circle) and friends. `Badge` variants `neutral`, `success`, `warning`, `destructive`, `info`, `verified`. Inputs are 44 px, 12 px radius, 16 px text on phones (no iOS zoom). Tabs are the pill segmented control; dialogs 480 px, 24 px radius; overlays use `scrim`; toasts use `toast-bg/fg`. Times use `TimePicker` (`src/components/elements`, shadcn's Popover with two scrolling columns, hours and minutes every 5, plus a saved odd minute; shadcn has no time picker), never `<input type="time">` on desktop (Ancung, 10 Nov). On touch screens (`useCoarsePointer`, `src/hooks`, `pointer: coarse`, not width) both use the device's own picker in a field styled like the others, as the design's B1.6 says, since the iOS and Android pickers suit a finger better. Dropdowns use `ChoiceSelect` (`src/components/elements`, shadcn's `Select` on Base UI with `items`, so the chosen label shows); an option can carry a 16 px `icon`, shown before its label in the list and in the field (on touch screens, where the device's list can't show icons, the picked one's sits inside the field), used by the Builder's tool picker (`builderToolIcon`: an app's own logo from `APPS`, else a plain icon; Ancung, 11 Nov) and the If's "Look at", where each result carries its step's icon (a tool's, or the website's or the Mind's block icon), never the browser's own `<select>` (Ancung, 9 Nov: the native list looked out of place); the `Select` trigger is 44 px like inputs. Re-adding a component with the shadcn CLI overwrites these edits, so diff before you accept.
- `AppProviders` wraps the app in `ThemeProvider` (class on `<html>`, so `<html suppressHydrationWarning>`), `QueryClientProvider`, `NearProvider`, `TooltipProvider` and sonner's `Toaster`.
- Colors: `src/styles/globals.css` holds the design's Stone & Lime tokens (copied from the variables in `design/hellonear.pen`), light in `:root`, dark in `.dark`. shadcn names are filled from them (`background` = bg, `card`/`popover` = surface, `muted`/`secondary` = surface-muted, `muted-foreground` = text-secondary, `destructive` = danger, `input` = border-strong, `ring` = focus). shadcn's `accent` stays a quiet hover grey, so **the design's lime `accent` is `brand` here** (`bg-brand`, `text-on-brand`, `bg-brand-soft`, `text-brand-strong`). Other design tokens keep their names: `surface`, `surface-hover`, `border-strong`, `tertiary-foreground`, `success(-soft)`, `warning(-soft)`, `danger(-soft)`, `danger-fill`, `on-danger`, `info(-soft)`, `toast-bg/fg`, `scrim(-soft)`, `node-*`. Radius: `rounded-sm` 8, `md` 12, `lg` 16, `xl` 24. When the design changes a token, change it here too.

## Commands

```sh
bun install
bun run dev        # http://localhost:3000
bun run typecheck
bun run lint
bun run build
bun run test       # unit tests (vitest)
```

Env (`.env.example`, names only, no secrets; both are read when `next dev` / `next build` starts, so restart after changing them):
- `HELLONEAR_API_URL`: the backend that `/api/v1/*` is forwarded to in local dev (default `http://localhost:4000`; hosted demo `https://api.hellonear.xyz`).
- `NEXT_PUBLIC_API_URL`: set only for the hosted FE. The browser then calls the API directly instead of the proxy.

## Structure

```
app/                     routes only; each page renders one screen from src/modules
src/
  components/
    ui/                  low-level primitives
    elements/            shared building blocks (cards, badges, amounts...)
    layout/              app shell and navigation
  modules/<feature>/     components/ (screens + parts), hooks/, data/ (dummy data first)
                         minds (Choose a Mind), chat, runs (what a run did: events, step rows, reply text, tool words;
                         shared by chat, attack, live view and Autopilot), wallet (Wallet & Policy, the approval card's parts), graph (Live view / Mind Graph),
                         builder, autopilot, skills, connections, attack, settings
  hooks/                 hooks shared across modules (`useMediaQuery`, `useCoarsePointer`)
  lib/                   config (network), utils (cn, kept for the shadcn CLI's `components.json`), api clients,
                         formatting, storage (`readPref` / `writePref`, safe when storage is blocked), stream (the SSE
                         reader, `ownerTimeZone`), media (`MEDIA` breakpoints, `prefersReducedMotion`); `isApiCode` in api, queryKeys (every React Query key)
  providers/             AppProviders (NEAR Connect via near-connect-hooks, client only)
  styles/                globals.css (Tailwind + shadcn tokens)
  types/                 shared types
tests/                   unit tests
```

Routes: `/` sign in (`SignInScreen`, design L1 and T1.1; once signed in it opens the newest Mind, or `/minds/new` when there is none, except a try-out with no Mind yet, which stays: Back from Choose a Mind returns to sign-in, and the try-out button reads "Continue your try-out" and reuses that session instead of making a new one; Ancung, 9 Nov), `/minds/new` Choose a Mind, and `/minds/[mindId]/{chat,chat/[threadId],wallet,skills,autopilot,connections,attack,settings}` inside `AppShell`; `/minds/[mindId]` redirects to chat and an unknown Mind is not found. The Builder (`/autopilot/new`, `/autopilot/{job}`) opens from Autopilot (no nav item) and has no app shell: Mind pages sit in route groups, `(shell)` with `AppShell` in its layout and `(focus)` for the Builder, while `[mindId]/layout.tsx` keeps `MindGate` and `ChatRunProvider` for both (Ancung, 9 Nov: a page without the sidebar to focus; the design's B1 is full screen too). URLs didn't change.

App shell (`src/components/layout`, design N1): phone below 768 px (`md`) gets `MobileHeader` (menu with an amber dot while an approval waits, Mind switcher sheet) and a left drawer; tablet 768 to 1279 gets the 72 px rail whose top button opens the full sidebar over the page; desktop from 1280 (`xl`) gets the 256 px sidebar that folds into the rail (saved in `localStorage` as `hellonear.sidebar.folded`). `MindSwitcher` and `AccountMenu` (Appearance System/Light/Dark, Sign out) each have trigger variants for these places. Nav items live in `nav.ts`. In the full sidebar and the phone drawer the menu and Recent chats scroll together, with the scrollbar on the sidebar's edge (`SidebarScroll`, decided 9 Nov with Ancung, like Claude; before, only Recent chats scrolled); the logo, the Mind and the account stay put. Where more of the menu is hidden above or below, it fades into the sidebar's colour (24 px at the top, 32 px at the bottom), stopping short of the scrollbar, like the chat under its header (Ancung, 11 Nov); each fade shows only when there is something to scroll to on that side.

Minds data (`src/modules/minds`): `api.ts` calls `GET /minds` and threads; each module calls its own routes (`wallet/api.ts` `walletApi` for the wallet, policy, payments and approvals, `skills/api.ts`, `connections/api.ts`). The shell reads each Mind's `GET …/wallet` (`null` on 404 `no_wallet`), `GET …/approvals` and `GET …/threads`; `hooks/useMinds.ts` turns them into what the shell shows (`Mind`, `RecentChat` in `data/minds.ts`) and only runs with a session. A wallet that can't be read (e.g. 502 `outlayer_error`) leaves the Mind listed without a balance. The fields inside `policy` can each be `null` (a policy set in the OutLayer dashboard without them; James, #79), so guard them wherever they are shown. Approvals refresh every 30 s. Balances show two decimals rounded down (`formatNear` in `src/lib/format.ts`); Recent chats show `shortWhen` (Today, Yesterday, weekday, date). Template labels and images come from `templateLabel` / `templateImage` (unknown template ids fall back to the General Assistant image). Mind images are in `public/minds/` (from the design): the 1408 x 768 art for cards, and a 512 x 512 centre crop `<id>-avatar.jpg` (`templateAvatar`) for every round avatar and the live view's centre, at quality 90 (`images.qualities` in `next.config.js`) with `sizes` set to the size it really shows at (`MindAvatar` `shown`). With the wide art, next/image picked a width, so a 40 px circle got an 80 x 44 image blown up and the graph squashed it (Ancung, 10 Nov). Circles of 40 px and under, and the live view's centre, use a head-and-shoulders crop `<id>-face.jpg` (`templateFace`, 256 x 256 from the avatar's 340 px around the head, made with sharp): the whole body at that size turned its knit, coins and straps into specks and left the face about 15 px (Ancung, 11 Nov). Larger ones keep the whole body. Page titles read "Chat | HelloNear", no "·".

`MindGate` wraps every `/minds/[mindId]` screen: no session goes back to `/`, and a Mind that isn't one of the user's (unknown, deleted, someone else's) is the not-found page (E1.3). It runs in the browser because on the hosted site the session cookie belongs to the API's host. Signing out from anywhere lands back on `/`. Back can still open a Mind of an earlier session (sign out, leaving a try-out, Connect Meteor). `MindGate` sends a Mind that isn't the user's to `/` (the current account's newest Mind) instead of not-found when it was reached with Back or Forward (`cameByHistory`, `src/lib/historyNav.ts`: a recent popstate, or a page load of type `back_forward`) or its session ended in this tab (`sessionStorage` `hellonear.leftMinds`, `src/modules/auth/data/leftMinds.ts`). A typed or clicked link to someone else's Mind still gets not-found (E1.3). Sign out uses `router.replace`, so the signed-out page leaves Back's history (Ancung, 9 Nov: Back from Choose a Mind showed a 404). `AppProviders` imports `historyNav` so it listens from the first page; imported only by `MindGate`, it missed a Back from Choose a Mind. Checked 9 Nov in Chrome: Back after signing out of a try-out, a Back within the app, and a Back that reloads the page all land on the current account's page; a typed link still gets the 404.

New Mind (`/minds/new`, `NewMindFlow`): needs a session (else back to `/`) and holds every value, so Back keeps what the user typed.
- Step 1, Choose a Mind (design L2, `ChooseMindStep`): `GET /templates` as three cards from 1280 px (`xl`) and a list below; card art shrinks on desktop screens shorter than the design's 960 px. The landing page's Choose buttons open `/minds/new?template=<id>`: a known id (`isKnownTemplate`) starts picked, and a visitor who is not signed in yet keeps it through sign-in in `sessionStorage` `hellonear.pickTemplate` (this tab only; checked 11 Nov in Chrome). Picking a template turns on the name field, which starts empty (no suggested names, decided 8 Nov). Name rule, checked as you type: 2 to 24 letters or numbers (stricter than the backend's 1 to 64). Card order and short skill labels live in `data/templates.ts`; the API's skill descriptions are written for the model, so skills without a label are not shown. Nothing is created here.
- Step 2, Set limits (design L3, `SetLimitsStep`): per-payment limit (starts at 2 NEAR, above 0 and at most 10) and 1 to 20 testnet accounts it may pay (no notes: the backend keeps only the list; starts with one empty row). Rules in `data/limits.ts` match `apps/be/src/wallets.ts`. "Create {name} and sign" runs `useSetUpMind`: `POST /minds`, `POST …/wallet` (409 `wallet_exists` is fine), `POST …/wallet/policy`, the owner signs the returned `store_wallet_policy` transaction (`useOwnerTransaction` in `src/modules/wallet`, signer = the session's account; a wallet on another account is refused before signing), then `GET …/wallet` until the policy shows (6 tries, 1.5 s apart, `readWalletUntil` in `wallet/data/ownerAction.ts`, which every owner action uses). The Mind and wallet must exist before there is anything to sign, so if signing is canceled they stay (decided 8 Nov): "Try again" resumes without creating a second Mind, and Back is hidden from then on. Leaving the page then leaves a Mind without limits; the Wallet screen will have to offer "Set limits".
- Ready (L3.5, `MindReady`): repeats the limit read back from the wallet, then "Say hi to {name}" opens the chat.
- Try-out users can't sign (`demo_not_allowed`) and pay from the shared demo wallet, so Continue on step 1 creates the Mind and opens its chat. For them the header shows no step count and the line under the name says "Next: start chatting".
- There is always a way out at the top right (Ancung, 9 Nov: a try-out landed here with no way back): "Use a wallet instead" for a try-out (ends it, back to sign-in), "Back to {name}" for an owner making another Mind, "Sign out" for an owner with none yet.
- Proven 8 Nov: the whole flow with Meteor (testnet) from `http://localhost:3000` against the hosted API, after #75 (the contract now wants `version`, `locked`, `valid_until`): tx `98ZP3dzZMNCVB1tfPDMnpNDVNr8NzR3GDaskdPHPaxvq`, and the policy read back from `GET …/wallet` before the ready screen. Not checked yet: canceling in Meteor, a wallet on another account, other wallets.

Chat (`/minds/[mindId]/chat` and `/chat/[threadId]`, `src/modules/chat`, design "4 · Chat" C1):
- `ChatRunProvider` (in the Mind layout) holds the one run in progress per Mind, so the stream survives the move from `/chat` to `/chat/{threadId}` once `run.started` gives the new thread its id (`router.replace`). Until that move lands, `/chat` keeps showing the run it started (`ActiveRun.newThread`, newer than the page), even after the reply finished; a later "New chat" page doesn't show it (Ancung, 9 Nov: the empty first-chat screen flashed between the reply and the move). Approve/decline resumes go through it too, so the live view and the Approvals badge can read the same run.
- `api.ts` posts chat and approve/decline and reads the SSE answer with `eventsource-parser`; an error before the stream starts throws `ApiError` from the JSON body. Both send the browser's `timeZone` (`ownerTimeZone`, #112), so the engine's `get_time` uses the owner's clock (it was never sent before 9 Nov, so every run was UTC). Not fixed by this: a model that schedules without calling `get_time` can still write `+00:00` (seen 9 Nov, raised with Axel); the approval card shows the time on the owner's clock, so it shows.
- `runs/data/events.ts` `foldRun` turns one run's §3 events into what the chat shows (text, tool steps, TEE badge, error; thinking a model sends as text, up to a closing `</think>`, becomes a thought row, Ancung, 11 Nov); the same fold serves a live stream and `GET /runs/{runId}`. A paused run's stream still ends with `run.finished` and `run.verified` and the backend keeps it `awaiting_approval`, so only new work after the pause (step, text, another tool) counts as resumed; a resumed run with no result for the tool was declined (`engine/test/engine.test.ts`: decline never writes a `tool.result`). `send_payment` refusals come as `policy_denied` / `wallet_frozen`, as the event status or the result's own status. A `tool.called` with `approvedBy: "rule"` (#167) marks its step `approvedByRule`: the step row says "Approved by your rule" and a sent payment's receipt says it went without asking. A result that is really a failure, Mastra's `{ error: true, message }` (the arguments failed validation, nothing ran) or a tool's own `status: "refused"` (a Sheets change refused, #245), is an error step (it read "Changed cells ✓" before, 11 Nov). A `send_payment` result whose own status is `failed` (a try-out's demo limit, OutLayer erroring) is an error step and shows "not sent", never "Sent" (11 Nov). An approval that comes after a resume (a split bill's next person) starts a new pause: approvals from the earlier pause that never ran are declined, the new one waits with its card (11 Nov; before, it read "you declined" and had no card).
- `useThread` reads `…/messages` (pages of whole runs, "Show earlier messages") and each run's events, and pairs them per run.
- Cards: a receipt for a sent payment (limit from the stored policy, NearBlocks testnet link `testnet.nearblocks.io/txns/{hash}`, the explorer docs.near.org lists for testnet), a red card for a refused one (which limit, read against the policy; never a tx link), an approval card answered in place (decided 9 Nov with Ancung; the design sent "Review and approve" to Approvals): the same checks as Approvals and Approve only when nothing would refuse it, otherwise a button to the fix. Frozen wallets show a banner and a different composer note.
- Approval cards for things other than payments say what is being approved, from the tool's own arguments (`data/approvalDetails.ts`, `ApprovalDetailLines`, chat and Approvals): an event's title and time, a meeting's time, guests, whether it gets a Meet link, that it is added to the owner's Google Calendar, and that Google emails each guest an invite in the owner's name (`googlecalendar_create_meeting`, #97), a moved event's old and new time as From and To, saying nobody is emailed (`googlecalendar_move_event`, #247; the old time is what the Mind listed, and the engine refuses the move if the event has moved since), an email's subject and recipients (`mail_send`), "Email me" with its subject, only to the owner's own Gmail (`mail_send_to_owner`, in chat since #225), and for the track skills' apps (#211) a new Doc's title, text added at the end of an existing Doc with that Doc's title, length and the text (`googledocs_append_text`, #247), a Sheets row's values, a Notion page or row, a Notion row change (each property old → new, #247, same words as the backend's Telegram card), a Slack message with its channel, a Zoom meeting's topic, time on the owner's clock, length and "Nobody is invited" (`zoom_create_meeting`, #246), and what a Mind sells for how much (`sell_offer`). Times are shown on the owner's clock. The answer toast names the thing ("Declining the meeting", "Scheduled a meeting"), not the tool's progress words.
- Streaming follows design/CLAUDE.md: steady reveal by whole words (at least 220 characters a second, easing toward the speed that shows the backlog within 0.8 s instead of jumping to ten times the base, which sped up and stalled as text arrived in bursts; Ancung, 11 Nov: it read choppy). The reply is rendered block by block (`splitBlocks`: blank lines, never inside a code fence), each block memoised, so only the last one is parsed again while streaming, like Vercel's Streamdown, and the reveal can update every frame; with a 200 ms per-word fade (all at once with reduced motion), rendered as Markdown from the first word; a "**" or "`" that is still open is closed for now (`closeOpenMarks`) so the symbols never show (Ancung, 9 Nov). The Markdown components are made once per streaming state (`markdownParts`, `useMemo`): defined inline they were new functions every frame, React remounted the whole reply as it grew, every word restarted its fade and a streaming reply showed only its list bullets (Ancung, 10 Nov; hidden locally while the dev proxy held the stream back). Where the view sits (decided 9 Nov with Ancung, like Claude, instead of the design's follow-the-bottom): an old thread opens at its end; a message sent glides its turn to the top of the view (24 px below it, 60 px on phones to clear the round Live view button too, `pinGap`; the last turn's min-height leaves the same room, so scrolling to the very end lands where pinning did instead of under the top fade; Ancung, 10 Nov) (the last turn gets a min-height of the view) and the reply grows below without the view chasing it; "Latest" shows whenever there is more below. The scroll area runs to the bottom of the screen and the composer floats over it, so the scrollbar reaches the bottom like Claude's (Ancung, 10 Nov); the text fades out under the header (24 px) and into the composer through overlays in the page colour that stop short of the scrollbar (Ancung, 9 Nov, like Gemini; a mask used to do it and hid the scrollbar's ends), and the content keeps room for the composer (its height is measured); the chat header has no divider line, and the content has the same room at both ends so nothing is faded at the start or the end. Only sending moves the view: answering an approval keeps the turn's room below it (`ActiveRun.pinned`) and starts from the events already shown, so nothing shrinks and the view stays put (Ancung, 9 Nov). The TEE badge shows under each verified reply only, not in the chat header as in the design: verification is per run, and a header badge read like it covered the whole chat. The Mind's replies and the typing dots have no bubble, only the small avatar and name above (also 9 Nov). A reply is one block under that avatar in the order it happened (`RunView.parts`): what the Mind said, the card it needed (approval, then receipt or refusal), then what it said after; the avatar shows even when the Mind goes straight to a tool. A short thread starts at the top, not pinned to the bottom as in the design, and a chat from today has no "Today" label: day labels only show where the day changes or at the top of an older thread (decided 9 Nov with Ancung), reading Today, Yesterday, or the day spelled out ("Monday, 2 Nov", the year only when it isn't this one; Ancung, 11 Nov: the short "Mon" from Recent chats read like a code there).
- The Mind's work shows inside its reply, in order (decided 9 Nov with Ancung, instead of relying on the live view): a row per tool (`runs/components/ReplySteps.tsx` `StepRow`, words in `runs/data/tools.ts` and `runs/data/steps.ts`): "Checking the balance..." with a spinner and shimmer while it runs, then "Checked the balance 4.79 NEAR"; a row per stretch of reasoning (`ThoughtRow`, from `reasoning.delta`, GLM only): "Thinking..." then "Thought for 4s". Finished rows open to show what went in and came back as plain "Name: value" lines (no code font, per the UI rules). Once the reply is done, its step and thought rows fold into one line above it, "Worked for 20s, used 4 steps" (`StepsSummary`, `summaryLabel`), that opens to show them in order; approvals, receipts and refusals stay in place (Ancung, 9 Nov, like Claude). "Worked for" is `RunView.workMs`: first event to last, leaving out the gap where a paused run waited for the owner's approval (thinking time alone hid where a 20 s wait went). Each finished tool row shows how long it took (`stepDuration`, from `tool.called` to its result); a running row and the "Thinking..." dots count seconds from 3 s on (`Elapsed`, this device's clock). Typing dots only show when nothing else does, reading "Thinking..." for the whole wait (not "Sending...": in a payments app that reads like money moving). ## Backend and sign-in

- **Local dev** (`NEXT_PUBLIC_API_URL` unset): the browser calls `/api/v1/*` on our own origin and `next.config.js` forwards it to `HELLONEAR_API_URL`, so the `hn_session` cookie belongs to our origin. That is what lets `http://localhost:3000` sign in against the hosted API (its cookie is `SameSite=Lax` and `Secure`; Chrome and Firefox accept `Secure` on localhost, Safari is not checked yet). The backend still checks the forwarded `Origin` against its `FE_ORIGIN` list (#71), so a new FE origin must be added there.
- **Hosted** (`NEXT_PUBLIC_API_URL=https://api.hellonear.xyz`): the browser calls the API directly. It is the same site as `app.hellonear.xyz`, so the `SameSite=Lax` cookie is sent, and the backend sees each visitor's IP. Try-out limits are per IP (`cf-connecting-ip`), and through a proxy every visitor would share the host's IP (James, #73).
- **Hosting (#125):** `deploy/deploy.sh` builds this app on the deploying machine (`next build` with `NEXT_PUBLIC_API_URL`, the only build-time setting) and the demo box runs it with `next start` on port 3000 (`deploy/systemd/hellonear-fe.service`), behind the tunnel at `https://app.hellonear.xyz` (the apex `hellonear.xyz`, until the landing page is deployed, and the old `hellonear.jameshub.fun` redirect there, `next.config.js`). A merge to `main` deploys it with the backend and engine (`deploy/README.md`). A new build-time env var must be added to `deploy.sh` too, or the hosted build won't have it.
- Call the backend with `api()` from `src/lib/api.ts` (`credentials: "include"`, JSON). Failures throw `ApiError` with `status`, `code` (the backend's `error`) and `details`.
- Sign-in (`src/modules/auth`, NEP-413, `docs/api-contract.md` §7): connect a wallet if none is connected, `POST /auth/challenge`, the wallet signs exactly `{ message, recipient, nonce }` (nonce decoded from base64 to 32 bytes; recipient comes from the challenge, `hellonear.app` on the hosted demo), then `POST /auth/login`. `useSignIn` signs through `connector.wallet()` / `connector.connect()` because the hook's own `signNEP413Message` reads wallet state from the previous render. `useSession` is the `["session"]` query (`GET /me`, `null` on 401); `useSignOut` logs out, disconnects the wallet and clears the query cache. The account shown in the app is the session's `nearAccountId`, not the wallet's.
- `SignInScreen` (`/`, design "3 · Start" L1, T1.1): the forest photo from the design (Unsplash, saved as `public/sign-in/forest.jpg` so the page doesn't load it from outside; desktop only) with the "Your limits stay yours." caption, then three choices. **Meteor Wallet** (with Meteor's own logo, `MeteorLogo` in `AppLogos.tsx`, the icon the official manifest lists, copied as is) opens Meteor straight away (`connector.connect({ walletId: "meteor-wallet" })`, the id in the official manifest `hot-dao/near-selector`, read 9 Nov); **Other NEAR wallets** opens the NEAR Connect list; after an "or" divider, **Try without a wallet** (`POST /auth/demo`). The chosen button shows "Waiting for Meteor"; a canceled signature says "Sign-in was canceled in the wallet. Nothing changed." ## Conventions

- **Everything clickable shows a pointer cursor** (team rule, 6 Nov). `globals.css` sets it in the base layer for buttons, links, labels, tabs, menu items, options, switches, checkboxes and anything with `role="button"`; disabled gets `not-allowed`. If you make a clickable `div` or `span`, give it `role="button"` (and keyboard support) or `cursor-pointer`. Never use `cursor-default` on something clickable.
- **System messages are formal and plain** (Ancung, 10 Nov: toasts and errors sounded too chatty). Toasts get a short standard title ("Key saved", "Funds added", "Could not send your answer") with any detail in the description line. Errors say what failed and what to do: "Could not load the payments. Please try again later.", "No changes were made.", "Check your connection and try again."; no "Couldn't", "Try again in a moment", "Nothing changed; try again" or "Something went wrong on the way". Empty states are plain ("No transactions yet", "No pending approvals"). Product copy from the design (headlines, skill cards, chat intros) keeps its voice. No "·" separators anywhere on screen.
- Never hold or send the backend's API keys or grant tokens in the browser; the FE only talks to `apps/be`.
- Wording: say "policy stored on-chain, enforced in a TEE". A rejected transfer shows `policy_denied` and the rule, never a tx link.
- Verification badge follows `docs/api-contract.md` §4: `gateway_tee` (a normal chat run) shows "Verified via NEAR AI TEE gateway", `model_tee` shows "Verified private (model TEE)", anything else no badge. The badge opens a popover (`runs/components/VerifiedBadge.tsx`, Ancung, 11 Nov, like near.ai/models' "Private TEE" note): what was checked in plain words (a `gateway_tee` step is checked against the gateway TEE's Intel TDX attestation only; NVIDIA (GPU) and Intel (CPU) are named only for `model_tee`, Axel on #255), the model, how many steps with their completion ids to copy (`RunView.proof`, from `run.verified`'s `model` and `completionIds`), and links to docs.near.ai/cloud/verification and the open-source verifier. The signatures and attestation reports themselves need a NEAR AI key the browser doesn't have, so they aren't shown.
- Redacted secrets render as `••••`; never try to unredact.
- Use the event shapes in `docs/api-contract.md` (#7); do not invent fields.
- Visual Builder (#20): save the React Flow `{ nodes, edges }` in the canvas format of `docs/api-contract.md` §2 "Visual Builder workflows" (node types `trigger`, `agent`, `tool`, `http`, `condition`; condition edges use `sourceHandle: "then" | "else"`). Show the engine's `issues` on a 400. Light nodes up from `node.started` / `node.finished` (`node` = your canvas node id).
- Skill picker: offer every skill from the backend's `GET /v1/skills` (once it exists; `docs/api-contract.md` §7), with `status` and `note` shown, not only the template's skills. A Builder workflow can only use tools of skills the Mind has equipped (`tools` in that list).
- Autopilot (#21, schedule UI): toggle with `PUT …/autopilot` (`enabled`), show `nextFireAt` and `pausedFor` reasons, and a run history from `GET …/runs` (`trigger: autopilot | manual`, per-node status in run order; poll while a run is `running`). Scheduled runs have no live stream and no badge.
