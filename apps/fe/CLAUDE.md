# CLAUDE.md — apps/fe

Web app (Next.js App Router + NEAR Connect). Owner: Ancung. Design comes from Nabil (#10). Issues: #9, #13–#21.

**Update this file in the same PR whenever you change setup, commands, env vars, dependencies, routes, or FE conventions.** Root rules in `/CLAUDE.md` also apply.

## Stack

- Scaffold with `npx create-near-app@latest fe --frontend next-app --install` in a temporary folder, then move the files here (create-near-app refuses non-empty folders). The `near-dapp` agent skill still mentions removed options (`--contract ts`, `next-page`); follow the create-near-app README. Then delete the generated `package-lock.json` and run `bun install` (the repo uses Bun, see the root `CLAUDE.md`).
- Wallet: `@hot-labs/near-connect` 0.12.0 + `near-connect-hooks` 1.1.6, testnet. **Meteor Wallet is the primary wallet:** show it first and test every flow with it. Per the official manifest (`hot-dao/near-selector`, checked 2 Nov) it supports `signMessage`, `signAndSendTransaction(s)`, `signDelegateActions`, and testnet. Keep other wallets selectable for judges.
- Live view (Mind Graph): our own SVG with a `viewBox`, a fixed map like the design (Mind in the center, its nodes around it), not `react-force-graph-2d` (decided 6 Nov: lighter, responsive, and the lines can animate per the motion rules). Visual Builder (bonus): `@xyflow/react` 12.12.1.
- Data and state: `@tanstack/react-query` 5.106.1 for all server data (cache, polling, refresh after approve or freeze). **No global state library.** The current Mind's id lives in the URL (`/minds/[mindId]/…`), every screen reads the Mind through the same React Query hook (one fetch, shared cache), and the last used Mind is kept in `localStorage`. One React context holds the chat run in progress so the chat, the live view and the Approvals badge read the same events. Add `zustand` only if that context gets heavy.
- Streams: chat, approve/decline and builder runs are POST + SSE, so `EventSource` can't be used; read the `fetch` body with `eventsource-parser` 4.1.3.
- Forms: `react-hook-form` 7.91.0 + `zod` 4.6.7 + `@hookform/resolvers` 7.0.3 (validate as you type, as in the design).
- Toasts: `sonner` 2.0.8 (shadcn's). Theme: `next-themes` 0.4.6 (System, Light, Dark from the account menu). Mind replies: `react-markdown` 10.1.0 with `remark-gfm` 4.0.1 (tables, strikethrough, task lists, bare links; added 9 Nov when a reply's table showed as pipes). Wide tables scroll sideways inside the reply. Springs (Penny is ready, freeze, Builder drag): `motion` 14.10.0; everything else is CSS.
- Tests: `vitest` 5.1.0 (unit, `tests/*.test.ts`, config `vitest.config.mts`), `@playwright/test` 1.65.0 (flows).
- Motion: easing tokens are in `src/styles/globals.css` (`ease-out`, `ease-in-out`, `ease-drawer` utilities; Tailwind only emits them once used). Rules, durations and chat streaming: `design/CLAUDE.md` "Motion (v0.3)". shadcn components keep their own animation classes; set menus and popovers to grow from `--transform-origin` (Base UI provides it) and make exits faster than entries.
- Scaffolded with `create-near-app` 10.0.0 (`--frontend next-app`). All versions in `package.json` are pinned exactly; do not upgrade during the hackathon.
- `near-connect-hooks` 1.1.6 itself depends on `@hot-labs/near-connect` ^0.11.1, so `package.json` has `"overrides": { "@hot-labs/near-connect": "0.12.0" }` to keep one copy at 0.12.0 (0.12.0 only adds gas-key APIs; checked against the 0.11.4 type definitions). After changing it, delete `node_modules` and run `bun install` so no nested 0.11.x copy is left.
- Wallet order: on testnet the official manifest filters out HOT (no testnet support), so Meteor is already first in the NEAR Connect popup; no reordering code needed (checked 3 Nov).
- UI: Tailwind CSS 4 + shadcn/ui (`base-nova` style, `components.json`, CLI 4.23.0). Add components with `bunx shadcn@4.23.0 add <name>`; they land in `src/components/ui`. Fonts: Geist (`--font-geist-sans`) and Geist Mono (`--font-geist-mono`, wallet addresses only) via `next/font`; the theme maps `font-sans` / `font-mono` to them (named differently on purpose: `--font-sans: var(--font-sans)` refers to itself and can drop the font).
- Primitives in `src/components/ui` are shadcn's, restyled to the design's components (`design/hellonear.pen`, Atomic Components): `Button` variants `default` (primary), `secondary`/`outline`, `brand` (lime, sparingly), `destructive` (`danger-fill`), `ghost`, `link`; sizes `default` (44 px pill), `sm` (36), `icon` (40 circle) and friends. `Badge` variants `neutral`, `success`, `warning`, `destructive`, `info`, `verified`. Inputs are 44 px, 12 px radius, 16 px text on phones (no iOS zoom). Tabs are the pill segmented control; dialogs 480 px, 24 px radius; overlays use `scrim`; toasts use `toast-bg/fg`. Re-adding a component with the shadcn CLI overwrites these edits, so diff before you accept.
- `AppProviders` wraps the app in `ThemeProvider` (class on `<html>`, so `<html suppressHydrationWarning>`), `QueryClientProvider`, `NearProvider`, `TooltipProvider` and sonner's `Toaster`.
- Colors: `src/styles/globals.css` holds the design's Stone & Lime tokens (copied from the variables in `design/hellonear.pen`), light in `:root`, dark in `.dark`. shadcn names are filled from them (`background` = bg, `card`/`popover` = surface, `muted`/`secondary` = surface-muted, `muted-foreground` = text-secondary, `destructive` = danger, `input` = border-strong, `ring` = focus). shadcn's `accent` stays a quiet hover grey, so **the design's lime `accent` is `brand` here** (`bg-brand`, `text-on-brand`, `bg-brand-soft`, `text-brand-strong`). Other design tokens keep their names: `surface`, `surface-hover`, `border-strong`, `tertiary-foreground`, `success(-soft)`, `warning(-soft)`, `danger(-soft)`, `danger-fill`, `on-danger`, `info(-soft)`, `toast-bg/fg`, `scrim(-soft)`, `node-*`. Radius: `rounded-sm` 8, `md` 12, `lg` 16, `xl` 24. When the design changes a token, change it here too.

Env (`.env.example`, names only, no secrets; both are read when `next dev` / `next build` starts, so restart after changing them):
- `HELLONEAR_API_URL`: the backend that `/api/v1/*` is forwarded to in local dev (default `http://localhost:4000`; hosted demo `https://api-hellonear.jameshub.fun`).
- `NEXT_PUBLIC_API_URL`: set only for the hosted FE. The browser then calls the API directly instead of the proxy.

## Structure

```
app/                     routes only; each page renders one screen from src/modules
src/
  components/
    ui/                  low-level primitives
    elements/            shared building blocks (cards, badges, amounts...)
    layout/              app shell and navigation
  modules/<feature>/     components/ (screens + parts), hooks/, data/ (dummy data first)
                         minds (Choose a Mind), chat, bazaar, wallet (Wallet & Policy), graph (Live view / Mind Graph)
  hooks/                 hooks shared across modules
  lib/                   config (network), utils (cn), api clients, formatting
  providers/             AppProviders (NEAR Connect via near-connect-hooks, client only)
  styles/                globals.css (Tailwind + shadcn tokens)
  types/                 shared types
tests/                   unit tests
```

Routes: `/` sign in (`SignInScreen`, design L1 and T1.1; once signed in it opens the newest Mind, or `/minds/new` when there is none), `/minds/new` Choose a Mind, and `/minds/[mindId]/{chat,chat/[threadId],wallet,approvals,skills,autopilot,connections,attack,settings}` inside `AppShell`; `/minds/[mindId]` redirects to chat and an unknown Mind is not found. Builder will open from Autopilot (no nav item).

App shell (`src/components/layout`, design N1): phone below 768 px (`md`) gets `MobileHeader` (menu, Mind switcher sheet, Approvals count) and a left drawer; tablet 768 to 1279 gets the 72 px rail whose top button opens the full sidebar over the page; desktop from 1280 (`xl`) gets the 256 px sidebar that folds into the rail (saved in `localStorage` as `hellonear.sidebar.folded`). `MindSwitcher` and `AccountMenu` (Appearance System/Light/Dark, Sign out) each have trigger variants for these places. Nav items live in `nav.ts`. In the full sidebar and the phone drawer the menu and Recent chats scroll together, with the scrollbar on the sidebar's edge (`SidebarScroll`, decided 9 Nov with Ancung, like Claude; before, only Recent chats scrolled); the logo, the Mind and the account stay put.

Minds data (`src/modules/minds`): `api.ts` calls `GET /minds`, each Mind's `GET …/wallet` (`null` on 404 `no_wallet`), `GET …/approvals` and `GET …/threads`; `hooks/useMinds.ts` turns them into what the shell shows (`Mind`, `RecentChat` in `data/minds.ts`) and only runs with a session. A wallet that can't be read (e.g. 502 `outlayer_error`) leaves the Mind listed without a balance. The fields inside `policy` can each be `null` (a policy set in the OutLayer dashboard without them; James, #79), so guard them wherever they are shown. Approvals refresh every 30 s. Balances show two decimals rounded down (`formatNear` in `src/lib/format.ts`); Recent chats show `shortWhen` (Today, Yesterday, weekday, date). Template labels and images come from `templateLabel` / `templateImage` (unknown template ids fall back to the General Assistant image). Mind images are in `public/minds/` (from the design).

`MindGate` wraps every `/minds/[mindId]` screen: no session goes back to `/`, and a Mind that isn't one of the user's (unknown, deleted, someone else's) is the not-found page (E1.3). It runs in the browser because on the hosted site the session cookie belongs to the API's host. Signing out from anywhere lands back on `/`.

New Mind (`/minds/new`, `NewMindFlow`): needs a session (else back to `/`) and holds every value, so Back keeps what the user typed.
- Step 1, Choose a Mind (design L2, `ChooseMindStep`): `GET /templates` as three cards from 1280 px (`xl`) and a list below; card art shrinks on desktop screens shorter than the design's 960 px. Picking a template turns on the name field, which starts empty (no suggested names, decided 8 Nov). Name rule, checked as you type: 2 to 24 letters or numbers (stricter than the backend's 1 to 64). Card order and short skill labels live in `data/templates.ts`; the API's skill descriptions are written for the model, so skills without a label are not shown. Nothing is created here.
- Step 2, Set limits (design L3, `SetLimitsStep`): per-payment limit (starts at 2 NEAR, above 0 and at most 10) and 1 to 20 testnet accounts it may pay (no notes: the backend keeps only the list; starts with one empty row). Rules in `data/limits.ts` match `apps/be/src/wallets.ts`. "Create {name} and sign" runs `useSetUpMind`: `POST /minds`, `POST …/wallet` (409 `wallet_exists` is fine), `POST …/wallet/policy`, the owner signs the returned `store_wallet_policy` transaction (`useOwnerTransaction` in `src/modules/wallet`, signer = the session's account; a wallet on another account is refused before signing), then `GET …/wallet` until the policy shows (5 tries, 1.5 s apart). The Mind and wallet must exist before there is anything to sign, so if signing is canceled they stay (decided 8 Nov): "Try again" resumes without creating a second Mind, and Back is hidden from then on. Leaving the page then leaves a Mind without limits; the Wallet screen will have to offer "Set limits".
- Ready (L3.5, `MindReady`): repeats the limit read back from the wallet, then "Say hi to {name}" opens the chat.
- Try-out users can't sign (`demo_not_allowed`) and pay from the shared demo wallet, so Continue on step 1 creates the Mind and opens its chat. For them the header shows no step count and the line under the name says "Next: start chatting".
- There is always a way out at the top right (Ancung, 9 Nov: a try-out landed here with no way back): "Use a wallet instead" for a try-out (ends it, back to sign-in), "Back to {name}" for an owner making another Mind, "Sign out" for an owner with none yet.
- Proven 8 Nov: the whole flow with Meteor (testnet) from `http://localhost:3000` against the hosted API, after #75 (the contract now wants `version`, `locked`, `valid_until`): tx `98ZP3dzZMNCVB1tfPDMnpNDVNr8NzR3GDaskdPHPaxvq`, and the policy read back from `GET …/wallet` before the ready screen. Not checked yet: canceling in Meteor, a wallet on another account, other wallets.

Chat (`/minds/[mindId]/chat` and `/chat/[threadId]`, `src/modules/chat`, design "4 · Chat" C1):
- `ChatRunProvider` (in the Mind layout) holds the one run in progress per Mind, so the stream survives the move from `/chat` to `/chat/{threadId}` once `run.started` gives the new thread its id (`router.replace`). Until that move lands, `/chat` keeps showing the run it started (`ActiveRun.newThread`, newer than the page), even after the reply finished; a later "New chat" page doesn't show it (Ancung, 9 Nov: the empty first-chat screen flashed between the reply and the move). Approve/decline resumes go through it too, so the live view and the Approvals badge can read the same run.
- `api.ts` posts chat and approve/decline and reads the SSE answer with `eventsource-parser`; an error before the stream starts throws `ApiError` from the JSON body.
- `data/events.ts` `foldRun` turns one run's §3 events into what the chat shows (text, tool steps, TEE badge, error); the same fold serves a live stream and `GET /runs/{runId}`. A paused run's stream still ends with `run.finished` and `run.verified` and the backend keeps it `awaiting_approval`, so only new work after the pause (step, text, another tool) counts as resumed; a resumed run with no result for the tool was declined (`engine/test/engine.test.ts`: decline never writes a `tool.result`). `send_payment` refusals come as `policy_denied` / `wallet_frozen`, as the event status or the result's own status.
- `useThread` reads `…/messages` (pages of whole runs, "Show earlier messages") and each run's events, and pairs them per run.
- Cards: a receipt for a sent payment (limit from the stored policy, NearBlocks testnet link `testnet.nearblocks.io/txns/{hash}`, the explorer docs.near.org lists for testnet), a red card for a refused one (which limit, read against the policy; never a tx link), an approval card answered in place (decided 9 Nov with Ancung; the design sent "Review and approve" to Approvals): the same checks as Approvals and Approve only when nothing would refuse it, otherwise a button to the fix. Frozen wallets show a banner and a different composer note.
- Streaming follows design/CLAUDE.md: steady reveal with a per-word fade (all at once with reduced motion), rendered as Markdown from the first word; a "**" or "`" that is still open is closed for now (`closeOpenMarks`) so the symbols never show (Ancung, 9 Nov). Where the view sits (decided 9 Nov with Ancung, like Claude, instead of the design's follow-the-bottom): an old thread opens at its end; a message sent glides its turn to the top of the view (the last turn gets a min-height of the view) and the reply grows below without the view chasing it; "Latest" shows whenever there is more below. The text fades out over 24 px under the header and 48 px above the composer (a mask on the scroll area, like Gemini; Ancung, 9 Nov); the chat header has no divider line, and the content has the same room at both ends so nothing is faded at the start or the end. Only sending moves the view: answering an approval keeps the turn's room below it (`ActiveRun.pinned`) and starts from the events already shown, so nothing shrinks and the view stays put (Ancung, 9 Nov). The TEE badge shows under each verified reply only, not in the chat header as in the design: verification is per run, and a header badge read like it covered the whole chat. The Mind's replies and the typing dots have no bubble, only the small avatar and name above (also 9 Nov). A reply is one block under that avatar in the order it happened (`RunView.parts`): what the Mind said, the card it needed (approval, then receipt or refusal), then what it said after; the avatar shows even when the Mind goes straight to a tool. A short thread starts at the top, not pinned to the bottom as in the design, and a chat from today has no "Today" label: day labels only show where the day changes or at the top of an older thread (decided 9 Nov with Ancung).
- The Mind's work shows inside its reply, in order (decided 9 Nov with Ancung, instead of relying on the live view): a row per tool (`ReplySteps.tsx` `StepRow`, words in `data/steps.ts`): "Checking the balance..." with a spinner and shimmer while it runs, then "Checked the balance 4.79 NEAR"; a row per stretch of reasoning (`ThoughtRow`, from `reasoning.delta`, GLM only): "Thinking..." then "Thought for 4s". Finished rows open to show what went in and came back as plain "Name: value" lines (no code font, per the UI rules). Once the reply is done, its step and thought rows fold into one line above it, "Worked for 20s, used 4 steps" (`StepsSummary`, `summaryLabel`), that opens to show them in order; approvals, receipts and refusals stay in place (Ancung, 9 Nov, like Claude). "Worked for" is `RunView.workMs`: first event to last, leaving out the gap where a paused run waited for the owner's approval (thinking time alone hid where a 20 s wait went). Each finished tool row shows how long it took (`stepDuration`, from `tool.called` to its result); a running row and the "Thinking..." dots count seconds from 3 s on (`Elapsed`, this device's clock). Typing dots only show when nothing else does, reading "Thinking..." for the whole wait (not "Sending...": in a payments app that reads like money moving). Thought rows have no icon, and opened details sit level with the row as plain muted text, no box. No "·" separators in these rows (Ancung). Reduced motion keeps a fading pulse instead of movement (`typing-dot`, `text-shimmer` in `globals.css`).
- No Stop yet: the backend has no cancel route and reads the engine to the end anyway, so Send waits while the Mind replies.
- First-chat copy (C1.2) is from the design for the Payments Mind; the Email Manager and General Assistant lines in `data/intro.ts` follow its pattern and still need Nabil's review. The design's third Payments suggestion ("Add 10 NEAR to your wallet") was swapped for "What's my balance?": adding funds is an owner action the Mind can't do.

## Backend and sign-in

- **Local dev** (`NEXT_PUBLIC_API_URL` unset): the browser calls `/api/v1/*` on our own origin and `next.config.js` forwards it to `HELLONEAR_API_URL`, so the `hn_session` cookie belongs to our origin. That is what lets `http://localhost:3000` sign in against the hosted API (its cookie is `SameSite=Lax` and `Secure`; Chrome and Firefox accept `Secure` on localhost, Safari is not checked yet). The backend still checks the forwarded `Origin` against its `FE_ORIGIN` list (#71), so a new FE origin must be added there.
- **Hosted** (`NEXT_PUBLIC_API_URL=https://api-hellonear.jameshub.fun`): the browser calls the API directly. It is the same site as `hellonear.jameshub.fun`, so the `SameSite=Lax` cookie is sent, and the backend sees each visitor's IP. ## Conventions

- **Everything clickable shows a pointer cursor** (team rule, 6 Nov). `globals.css` sets it in the base layer for buttons, links, labels, tabs, menu items, options, switches, checkboxes and anything with `role="button"`; disabled gets `not-allowed`. If you make a clickable `div` or `span`, give it `role="button"` (and keyboard support) or `cursor-pointer`. Never use `cursor-default` on something clickable.
- Never hold or send the backend's API keys or grant tokens in the browser; the FE only talks to `apps/be`.
- Wording: say "policy stored on-chain, enforced in a TEE". A rejected transfer shows `policy_denied` and the rule, never a tx link.
- Verification badge follows `docs/api-contract.md` §4: `gateway_tee` (a normal chat run) shows "Verified via NEAR AI TEE gateway", `model_tee` shows "Verified private (model TEE)", anything else no badge.
- Redacted secrets render as `••••`; never try to unredact.
- Use the event shapes in `docs/api-contract.md` (#7); do not invent fields.
- Visual Builder (#20): save the React Flow `{ nodes, edges }` in the canvas format of `docs/api-contract.md` §2 "Visual Builder workflows" (node types `trigger`, `agent`, `tool`, `http`, `condition`; condition edges use `sourceHandle: "then" | "else"`). Show the engine's `issues` on a 400. Light nodes up from `node.started` / `node.finished` (`node` = your canvas node id).
- Skill picker: offer every skill from the backend's `GET /v1/skills` (once it exists; `docs/api-contract.md` §7), with `status` and `note` shown, not only the template's skills. A Builder workflow can only use tools of skills the Mind has equipped (`tools` in that list).
- Autopilot (#21, schedule UI): toggle with `PUT …/autopilot` (`enabled`), show `nextFireAt` and `pausedFor` reasons, and a run history from `GET …/runs` (`trigger: autopilot | manual`, per-node status in run order; poll while a run is `running`). Scheduled runs have no live stream and no badge.
