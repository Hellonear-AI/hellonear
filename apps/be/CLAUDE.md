# CLAUDE.md — apps/be

Backend API: Postgres + pgvector, NEP-413 login, run/event storage + SSE, encrypted secret store, OutLayer, Composio and AgentMail integration. Owner: James. Issues: #6, #7, #8, #13–#18.

**Update this file in the same PR whenever you change setup, commands, env vars, the DB schema, endpoints, or BE conventions.** Root rules in `/CLAUDE.md` also apply.

## Stack

- Plain `node:http` + `zod` + `pg`, like the engine; tests with `node:test`. Runtime **Node ≥ 24.22.1**, package manager **Bun** (`bun.lock`). Versions pinned in `package.json`; do not upgrade during the hackathon.
- `near-api-js` 7.4.0. Auth: `near-api-js/nep413` `verifyMessage` (main), `near-sign-verify` (alternative).
- OutLayer on **testnet** (`https://testnet-api.outlayer.ai`). Intents routes (`/intents/*`, swaps, limit orders) are mainnet-only and out of scope.
- Composio REST **v3.1** (`https://backend.composio.dev/api/v3.1`, header `x-api-key`, a **project** key `ak_…`; a personal "For you" `ck_…` key gets `401`). The backend calls it with `fetch` (no SDK): Connect Links, status, delete (`src/connections.ts`). Tool execution happens in the engine through a per-user Session (calls outside a Session are capped at 10K/month).

## Conventions

- Store OutLayer `wk_...` keys and Composio/OAuth tokens encrypted; never log them, never return them to the FE, never pass them into prompts.
- Per-skill wallet = an OutLayer **sub-wallet** (`PUT /wallet/v1/api-key` creates a new wallet with its own address and balance). Fund it from a whitelisted parent; move the balance back before revoking.
- Owner actions (policy changes, `freeze_wallet()`) are signed by the owner's NEAR account (the team uses Meteor Wallet on testnet), not by the backend. They are calls on the `outlayer.testnet` contract (`store_wallet_policy`, `freeze_wallet`, `unfreeze_wallet`; view `get_wallet_policies_by_owner`), so they have tx hashes; the backend can prepare them (it encrypts and signs a policy with the agent key) and the owner signs them in our FE (spike README, "Owner actions on-chain"). **Meteor works with the OutLayer dashboard** (#6, 4 Nov): it connected and signed the policy, an approval and the freeze. The dashboard defaults to mainnet; it reads `localStorage["near-wallet-selector:selectedNetworkId"]`, so pick testnet first or a testnet key shows "Invalid or revoked API key".
- OutLayer answers (spike `spikes/01-outlayer/`): over the per-transaction limit or off the whitelist → `403 policy_denied`; frozen → `403 wallet_frozen`; both happen before signing, so there is no tx for the refused transfer. When the owner's policy has an approval threshold (`approval.threshold.required`), a transfer under the limit comes back `200 { status: "pending_approval", approval_id }`: poll `GET /wallet/v1/requests/{id}` until `success` (with `tx_hash`) or `failed`.
- **Decided (4 Nov): approval lives in the app, OutLayer is the hard stop.** Mind wallets use policy v2 (`spikes/01-outlayer/README.md`): per-transaction limit, whitelist, `transaction_types: ["transfer"]`, and `transfer` excluded from OutLayer approval (the dashboard only offers approval per transaction type, not above an amount, so leaving it on would make the owner approve every payment twice). The approval inbox is the engine's `tool.approval_required` flow.
- **Decided (#15, 5 Nov): the `handoff_url` never leaves the backend and is not stored** (it carries the `wk_` key). Owners act from our FE: `src/wallets.ts` builds `store_wallet_policy` (encrypt-policy + sign-policy with the agent key; since 8 Nov the contract wants `version`, `locked` and `valid_until` too, which the keystore signs into `store_wallet_policy:v2:…` and returns from sign-policy: pass them through unchanged, or the contract panics `missing field version` / `policy version is N` / `signature expired`; source `fastnear/near-outlayer` `contract/src/wallet.rs`; deposit from `estimate_wallet_policy_cost`), `freeze_wallet` and `unfreeze_wallet` as NEAR Connect transactions for the owner to sign. `wallet_pubkey` is `ed25519:` + `sign-policy`'s `public_key_hex` (= the wallet's implicit account), **not** `encrypt-policy`'s `wallet_pubkey`, which is the wallet UUID. One wallet per Mind in `mind_wallets`, key AAD `wallet:{mindId}`. Tests use `test/fake-outlayer.ts` (it also answers the RPC view at `NEAR_RPC_URL`).
- Use per-transaction limits, whitelist, multisig, or freeze for hard stops; cumulative (daily) limits can be exceeded under parallel requests (OutLayer's gateway counts, the TEE keeps no state). **Daily cap (#149):** optional `dailyNear` in policy v2 → `rules.limits.daily.native`. Proven on testnet (10 Nov, throwaway wallet): over it → `403 policy_denied` "Daily limit exceeded for native: spent + amount > cap", no tx; exactly at the cap goes through; a refused request does not count. `GET /wallet/v1/policy` returns the counter as `usage.daily.native.spent` (`{}` before the first payment); `GET …/wallet` returns it as `spentTodayNear`. Reset time (00:00 UTC or rolling 24 h) not proven yet.
- Every route checks that the user owns the Mind/agent it touches (`requireMind`, `getRun`). Another user's Mind answers `404`, never `403`.
- Login: one-time nonce consumed atomically before the signature check; `verifyMessage` also rejects function-call keys. Sessions: only `sha256(token)` is stored; cookie `hn_session`, `HttpOnly`, `SameSite=Lax`, `Secure` when `COOKIE_SECURE=true`. State-changing requests whose `Origin` is not in `FE_ORIGIN` get `403` (CSRF). `FE_ORIGIN` may list several origins, comma-separated and matched exactly (e.g. the public FE plus `http://localhost:3000` for local FE work against the hosted API); the first is the Composio callback origin.
- **Thread ids are issued by the backend** (`thr_…`). A `threadId` from the browser is only accepted if a run of that same Mind already used it: engine memory is keyed by thread, so a foreign id would read another Mind's history.
- The chat relay (`src/runs.ts`) reads the engine stream to the end even when the browser leaves, so `run_events` is complete. Store every event before forwarding it; deltas are batched. A resumed run continues the paused run's `seq`; if the engine restarted (its counter is in memory) the backend shifts the new events after the stored ones.
- **Cancel (#121):** each relayed run gets an `AbortController` (passed to `engineFetch` as `signal`, kept in the in-memory `live` map in `src/runs.ts` once its `runId` is known). `POST /v1/runs/{id}/cancel` aborts it; the relay then stores `run.finished` `{ status: "canceled" }` (builder: `workflow.finished`) as the last event, sets `runs.status = 'canceled'` and ends the stream, and the route answers once that is stored. A browser leaving still does **not** cancel. Not live (finished, paused, or after a restart): `409 not_running`; a paused run is declined, not canceled. Single process only: with more than one backend process the map would have to move to Postgres.
- Secrets: AES-256-GCM with `SECRETS_MASTER_KEY`, AAD `userId:name`. Never return values, never log them, decrypt only in `secretsForRun` for one engine call. Host rules match the engine's (`allowedHosts`, lowercase host names, no scheme/port/path).
- Chat threads (#54, `src/threads.ts`) come from the backend's own `runs.user_message` and `text.delta` events, never from the engine's `mastra` schema. Titles are the newest `thread.titled` event's `title` (#86, a short summary from the engine; read from `run_events`, no column of its own), else the first user message, both cut to ~60 characters by `titleOf` (Mastra keeps none). Messages page by whole runs; the cursor is `<ISO time>~<runId>`, compared at millisecond precision (Postgres keeps microseconds, JS dates do not). No thread delete yet: it would need an engine route to drop the thread's memory too.
- **Time zone (#112):** chat, approve/decline and builder workflow runs take an optional `timeZone` (IANA, from the browser), checked with `Intl.DateTimeFormat` and forwarded to the engine as `timeZone`; an unknown name is `400` and never reaches the engine. Not stored: Autopilot runs have no browser, so they stay in UTC for now.
- Approve/decline only for a run in `awaiting_approval` whose `tool.approval_required` event has that `toolCallId` (`409` otherwise).
- Deleting a Mind deletes its engine workflows first (which removes their Autopilot schedules).
- **Upstream failures answer `503`, never `502`** (`UPSTREAM_ERROR` in `src/http.ts`). Cloudflare replaces a `502`/`504` body from the origin with its own HTML page (pass-through is Enterprise-only), so the FE would lose `{ error, ...details }` (8 Nov, a Mind wallet that failed to create). `…_unreachable` errors carry `reason` (`fetchFailure`). Every 5xx is logged as one `http error` line (`logServerError`: route without query, code, details); never put keys or upstream bodies in `details`. Check with `journalctl -u hellonear-be | grep 'http error'` on the hosted demo.
- Schema and events follow `docs/api-contract.md` (#7).
- Builder workflows (#20) are stored by the engine; the backend proxies `…/workflows` calls after the ownership check and sends the Mind config and secrets on each run, as for chat.
- A Mind's skills are validated against the engine's `GET /v1/skills` (the whole catalog, cached 60 s), not the skills templates offer: `near-account` and `http-request` are in no template but the Visual Builder needs them. The backend's own `GET /v1/skills` returns the same list for the skill picker.
- **Decided (#42): option B.** The engine's payment tools call `/internal/v1/wallet/*` with `X-Engine-Key` and a wallet token (`src/walletToken.ts`: HMAC with a key derived from `SECRETS_MASTER_KEY`, one Mind, 15 min). The backend adds `walletToken` to chat, approve/decline and builder runs only when the Mind has a wallet; never to Autopilot. `src/payments.ts` calls OutLayer and stores every attempt in `wallet_payments`. Internal routes sit before the session check and answer only on loopback (`isLoopback`, else `404`; the engine runs next to the backend, the tunnel comes from another host); keep all three checks.
- **Judge try-out mode (#43, `src/demo.ts`)**, on only with `DEMO_MODE=true`. `POST /v1/auth/demo` makes a fresh user (`is_demo`, `demo:<random>`, which no NEAR account can be). Limits in `config.demo`: 20 runs per user, 60 runs and 10 sign-ups per IP per hour (in memory, IP from `CF-Connecting-IP`: only the tunnel host can reach the backend), 2 payments per user that are sent or pending (checked and inserted in one transaction under a per-user advisory lock, `sendPayment`'s `cap`); the hourly windows are swept every 10 minutes. Owner actions (`denyDemo`) answer `403 demo_not_allowed`. Their Minds pay from the shared demo wallet (`DEMO_OUTLAYER_API_KEY`, `keyOf` in `src/wallets.ts`). Runs carry `demo: true` so the engine uses a sample inbox. Demo users are deleted after 7 days (at start and daily). Every finished run logs `run usage` (tokens, cost) to the journal.
- **Attack Playground (#129):** `POST /v1/attacks/{id}/runs` runs the engine's scenario on a hidden playground Mind per user and attack (`minds.playground_attack`, migration 008; `playgroundMind` in `src/minds.ts`). It counts as a demo Mind for the wallet (`isDemoMind`: shared demo wallet, and the payment cap counts only demo-wallet payments, so an owner's own payments don't use it up), runs with `demo: true` and `secrets: []`, is left out of `listMinds`, and every `/v1/minds/{id}` route answers 404 for it. Approve/decline add its `attackId` (`playgroundAttackOf`).
- App connections (#13): the Composio user id is our `users.id`, which the engine already receives as `userId`. Toolkits: `gmail`, `googlecalendar` (#57), `googlemeet` (#97, Meet links for the engine's `googlecalendar_create_meeting`; auth config `ac_ISu09_uuoKCK`, scopes `meetings.space.created` + `meetings.space.settings`) (`TOOLKITS` in `src/connections.ts`, slugs checked live against Composio). `POST /v1/connections/{toolkit}` creates a Tool Router session for that user and a Connect Link (callback `{FE_ORIGIN}/connections?toolkit={toolkit}`), removing unfinished attempts first; never trust the callback's query string, re-read `GET /v1/connections`. Composio-managed OAuth (no Google app of our own). Tests use `test/fake-composio.ts`.
- **Paid data (#150, `src/shop.ts`):** `GET /internal/v1/shop/{item}` answers 402 with a price and `SHOP_PAY_TO`; with `?tx=` it serves a live NEAR RPC report only for this Mind's own `sent` payment row (to `SHOP_PAY_TO`, at least the price, last hour), confirmed by RPC `tx` (success, signer = the Mind's wallet), and records the hash in `shop_purchases` (009) so it is used once. Plain `rpc.testnet.near.org` forgets transactions after a few days, hence the one-hour window. `SHOP_PAY_TO` must be on the paying wallet's address list. Tests use the fake OutLayer's `/rpc` (`tx`, `status`, `gas_price`).
- **Mind email addresses (#96, `src/mail.ts`):** AgentMail REST v0 with `fetch` (no SDK, like Composio): `POST /inboxes` with `client_id` = Mind id (retries return the same inbox; checked live 9 Nov), `POST /inboxes/{id}/messages/send` with an `Idempotency-Key` header, `GET /inboxes/{id}/messages[/{message_id}]`. An inbox is created only when the owner equips the `email-address` skill (`POST`/`PATCH /v1/minds` or `POST …/inbox`); one row per Mind in `mind_inboxes`, address `{name}-{6 id chars}@agentmail.to`. `key_slot` names the AgentMail key (organization) holding it: slot 0 `AGENTMAIL_API_KEY`, slot 1 `AGENTMAIL_API_KEY_2`; a `403 limit_exceeded` on create moves to the next slot (Free plan: 3 inboxes per organization). The engine's mail tools call `/internal/v1/mail/{send,messages,messages/{id}}` with `X-Engine-Key` and a **mail token** (`mt_…`, `src/walletToken.ts`, own HMAC key, 15 min, one Mind), added to runs only while the skill is on and the inbox exists; same three checks as the wallet routes. Every send is stored in `mail_sends` (refusals too); a retry with the same idempotency key (the engine's tool call id) maps to the same row id, so it is stored, listed and counted once. Caps: owners 20 sends per Mind per day; try-out users share `DEMO_AGENTMAIL_INBOX`, may only send to it, and get 2 sends each (per-user advisory lock, like `sendPayment`'s cap). AgentMail refusals keep their code: `429 rate_limit_exceeded` → `rate_limited`, `403 message_rejected`/`limit_exceeded`/suspended → `rejected` (send results), or `429 mail_rate_limited` / `403 mail_rejected` (other routes); a wrong key or anything else → `503 agentmail_error`. A message read is checked against the Mind's own `inbox_id`. **The shared try-out inbox is public** (anyone can mail it), so a try-out Mind only lists and reads messages whose `message_id` its own user's Minds sent (`mail_sends`); mail from anyone else is never shown. Deleting a Mind deletes its own AgentMail inbox first (`DELETE /inboxes/{id}`, asynchronous `202`), best effort: AgentMail down or `404` does not block the delete; the shared inbox is never deleted. **Email me (#146):** `POST /internal/v1/mail/owner` (engine key only, since Autopilot runs carry no mail token; body names `userId` and `mindId`, and the Mind must be theirs) sends to the address of the owner's connected Gmail, read with Composio `GMAIL_GET_PROFILE` (`gmailAddress` in `src/connections.ts`); the recipient is never in the request, try-out users are refused, the daily cap applies. Tests use `test/fake-agentmail.ts`; `test/agentmail-live.test.ts` is opt-in (`AGENTMAIL_LIVE=1`, creates/reuses only `hellonear-demo@agentmail.to`, sends to itself; `AGENTMAIL_LIVE_TO` adds one send to the account owner).
- Persona version (#116, migration 007): `updateMind` bumps `minds.persona_version` when the `name` or `soul` really changes (same value again, skills or model: no bump). `mindConfig` sends it as `mind.personaVersion` only when > 0, so Minds never renamed keep the engine's old memory id `userId:mindId`; the engine uses `userId:mindId:v{n}` otherwise.
- Autopilot (#21): `PUT …/workflows/{id}/autopilot` stores a copy of the Mind config in the engine. **Send it again for every Autopilot workflow of a Mind whenever that Mind changes** (persona, model, skills); a `409` means the engine paused it, show `pausedFor`. Scheduled runs get no secrets yet (`docs/api-contract.md` §6 q4).

## Commands

- `bun run dev` (port 4000, applies migrations at start), `bun run migrate`, `bun run test:unit` (offline), `bun run test` (unit + integration: local Postgres + fake engine), `bun run load` (fake engine; fails if a run loses events), `bun run typecheck`.
- Postgres: `docker compose up -d postgres` from the repo root; `docker compose stop` when done. If port 55432 is taken by another project, run it on another host port with a compose override (`ports: !override ["55433:5432"]`) and pass `DATABASE_URL=…:55433/hellonear` to `bun run test` / `bun run load`.
- Schema changes: add a new `migrations/NNN_name.sql` (never edit an applied one) and update `docs/api-contract.md` §5.
- Tests never call NEAR AI or the NEAR RPC: `test/fake-engine.ts` stands in for the engine and `setProvider()` fakes the access-key lookup; signatures are real. Run `bun run test` and `bun run load` before every push/merge that touches `apps/be`, and report results in the PR. CI: `.github/workflows/be.yml`.
- End-to-end checks against the real engine need `NEARAI_API_KEY` in `engine/.env`; a real wallet login needs `NEAR_TEST_ACCOUNT_ID` / `NEAR_TEST_PRIVATE_KEY` (`scripts/login-smoke.ts`).
