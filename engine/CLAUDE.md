# CLAUDE.md — engine/

AI engine: a Mastra server that runs each Mind (soul, skills, tools, memory, schedules) on NEAR AI Cloud models. Owner: Axel. Issues: #5, #11, #13–#21.

**Update this file in the same PR whenever you change setup, commands, env vars, the Mastra version, model choices, or engine conventions.** Root rules in `/CLAUDE.md` also apply.

## Stack

- `@mastra/core` **1.81.0, pinned.** Do not upgrade during the hackathon (dynamic workflows are Beta and the API moves fast).
- Models: NEAR AI Cloud (`NEARAI_API_KEY`). Default `z-ai/glm-5.3-flash`, reasoning `deepseek-ai/DeepSeek-V4.1-Flash-1017`, embeddings `Qwen/Qwen3-Embedding-0.6B`. Tool calling through Mastra is proven for both chat models (spike `spikes/01-tool-calling`, #5). Never fall back to a model without `tools` in `supportedFeatures` (e.g. GPT-6 Luna).
- **Build streaming chat models with `@ai-sdk/openai-compatible` and `includeUsage: true`** (`nearai.chatModel('<id>')`), not the `nearai/<id>` router string: the router string streams with empty token usage, and we need usage for per-step cost. See the spike README.
- Storage and memory: Postgres + pgvector.

## Conventions

- One generic Mind agent; per-Mind config comes from `RequestContext` (`@mastra/core/request-context`), not from separate agent definitions.
- Skills: parse `SKILL.md` frontmatter yourself, then call `createSkill({ name, description, instructions, ... })`. Restrict tools in the `tools` resolver (Mastra does not enforce `allowed-tools`).
- Multi-agent: supervisor/subagents. Do not use `.network()` (deprecated).
- Autopilot: use **workflow** schedules with `requestContext`; agent schedules do not accept it.
- Reasoning models spend part of `max_tokens` on reasoning; keep limits generous (a 5-token test returned empty `content`).
- **Context budget (#123, `src/mastra.ts`):** every model call's messages go through Mastra's `TokenLimiterProcessor` (`limit: config.contextTokenLimit`, env `CONTEXT_TOKEN_LIMIT`, default 12000, `trimMode: 'contiguous'`): when a long thread plus recalled memory passes the budget, the oldest messages are dropped first and the system prompt and tools stay. The limit counts messages only, so the prompt the model sees is ~2K tokens above it. Measured 9 Nov (local engine, 10-turn thread with a fact in turn 1, per-step input): default 12000 never trims (max 10.8K, same as main's 11.2K); with 6000 input plateaus at ~8K from turn 7 and the turn-1 fact is still recalled (semantic recall brings it back). Hosted p95 was 27.8K, max 38.2K, so the default caps the long tail only.
- **Reasoning effort (#92, `src/models.ts` `withReasoningEffort`):** models in `config.lowReasoningModels` (today `z-ai/glm-5.3-flash`) get `reasoning_effort: "low"` on every request (chat, resumed runs, workflows, titles), added in the provider's `transformRequestBody`. For GLM-5.3 Flash its reasoning budget otherwise defaults to 8192 tokens, above our 4096 output cap; one hosted run spent all 2048 on reasoning and wrote no reply. Measured 9 Nov (local engine, 3 runs each): every task still correct, tool runs 10.3 s → 3.4 s, inbox 33 s → 19 s, scam-message refusal 58 s → 9 s. Weakness seen once: summing 12 numbers in its head after a long thread came out wrong (default got it right); arithmetic belongs in `add_numbers`. A call can still set its own `reasoning_effort`.
- E2EE only works on `/chat/completions`, not the Responses API.
- **Verified private badge (#19):** chat models use the NEAR AI SDK fetch transport (`inferenceClient.fetch` in `src/models.ts`); never bypass it for chat, or responses cannot be verified. Verify only after the stream is fully read. Streaming gives `gateway` signatures, non-streaming gives `provider_tee` (measured 3 Nov); the badge level follows the weakest step (`src/verify.ts`). Incognito models never get the badge. Keep `maxRetries: 0`. Attestation is warmed at startup and every 50 minutes; a cold check is ~20 s.
- The SDK needs Node ≥ 24.22.1.
- Secrets (#18, `src/secrets.ts`): never put secret values in prompts. The model writes `{{secrets.NAME}}`; only tools fill it from `RequestContext` (`SECRETS_KEY`, never registered for tracing). Any new tool that sends data out must: fill secrets only at execution, call `assertHostAllowed`, `assertPublicHttpsUrl` and `assertResolvesPublic`, not follow redirects, and `redact` its result before returning. Events are redacted by value too (`SensitiveDataFilter` only matches field names, so it is not enough).
- After changing anything on the secrets path, run the secrets tests: they scan every table in the `mastra` schema for the test secret.
- Wallet tools: require approval (`requireApproval`); never expose owner actions (policy changes, freeze) as LLM tools.
- **Payment tools (#42, option B, `src/wallet.ts`):** `send_payment` (approval), `get_balance`, `list_payments` call the backend's `/internal/v1/wallet/*` routes with `X-Engine-Key` and the run's `walletToken` (`X-Wallet-Token`); the engine never holds an OutLayer key. The backend sends `walletToken` on chat, approve/decline and builder runs, never on Autopilot. Keep the token in `RequestContext` as a `Map` (`WALLET_KEY`), like secrets, and in the redaction list of every run (`hiddenValues` in `src/server.ts`); `test/engine.test.ts` checks it is in no event and no `mastra` table. No token → the tools throw "no wallet yet" without calling the backend. A `policy_denied` / `wallet_frozen` result becomes a `tool.error` event with that status: never show it as "rejected on-chain" or with a tx link.
- **Auto-approve rules (#167, `src/autoApprove.ts`):** the backend sends `mind.autoApprove` (`{ tools, payment?: { maxNear, recipients } }`); `ruleFor` decides per call. Every `requireApproval: true` tool (registry and `IN_CHAT`) gets a `needsApprovalFn` (assigned at the end of `src/tools.ts`), which Mastra 1.81 reads per call and treats as authoritative over the boolean (`resolveToolApprovalVerdict` and the tool-call step in `@mastra/core/dist/agent-*.js`, read 11 Nov); the boolean stays `true`, so `needsApproval`, `toolsFor` and the Builder still treat them as approval tools and Autopilot never gets them. Switches cover `SWITCHABLE_TOOLS` only; a payment runs without asking only at or under `maxNear` (yoctoNEAR `BigInt` compare) and only to an account in `recipients` (the policy's whitelist, filled by the backend per run; empty = always asks). `demo` runs (try-outs, Attack Playground) always ask. A payment after a failed one still goes to the gate, so `beforeApproval` refuses it. `tool.called` carries `approvedBy: "rule"` and `rule` from the same function (`rulesOf` in `src/server.ts`), so the chat can say the owner's rule approved it; the one mismatch is that blocked repeat payment, whose result says `failed`. The prompt states the rules (`autoApproveLine` in `src/mind.ts`, left out on `demo` runs in `src/mastra.ts`) and tells the Mind not to ask for or claim an approval for a call under a rule: without it the Mind wrote "please approve when the wallet asks" and "you approved it" for a payment its rule had sent (Chrome, 11 Nov). Tests: `test/auto-approve-rules.test.ts` (unit), `test/auto-approve.test.ts` (live, fake wallet: 6/6 on 11 Nov).
- **No payment after a failed one (11 Nov):** once `send_payment` throws or returns `failed` in a request, it marks that request's wallet `Map` (`markPaymentFailed`), and its `beforeApproval` answers every later `send_payment` in the same request with `status: "failed"` and no approval card (`paymentFailedEarlier`). Seen live in Chrome: after an error the model paid the next person in a split; the prompt rule alone held 4 of 6 runs. Every paying skill also says not to call it again. Tests: `test/wallet-tools.test.ts`, and the 503 case in `test/skills-wallet.test.ts`.
- **Money shares (`split_amount`, 11 Nov):** shares of a NEAR amount are worked out in yoctoNEAR `BigInt`s (`splitAmount` in `src/tools.ts`), each rounded down to 4 decimals, with `leftOver` for what rounding kept back; weights are percents or 1 each. `split-bill` and `revenue-split` must use it and pay exactly what it returns (a share of 0 is not paid). Seen in the full suite: a revenue split paid 0.002 and 0.003 for 40% and 60% of 0.05, the model doing the percent in its head. Tests: `test/tools.test.ts`, and the wallet live tests assert the tool was called.
- **Paid data (#150, `buy_data`, skill `paid-data`):** a 402 pattern on testnet NEAR. `buy_data` calls the backend's `/internal/v1/shop/{item}` with the wallet token (`walletCall` with `accept: [402, 409]`, so those are answers): `payment_required` (price, `payTo`), then after `send_payment` returns `sent`, the same call with `paymentTxHash` returns `paid` with the report and a receipt. The skill grants `send_payment` itself, so the owner's approval and the wallet policy guard every purchase. Graph: the wallet node.
- **Wallet skills (skills only, no new tools; prompt tests in `test/skills-wallet.test.ts` with a fake wallet backend):** `recipient-guard` (#182: `near_view_account`, `list_payments`, grants `send_payment` itself; a lookalike of an account paid before, e.g. `b0b.testnet` vs `bob.testnet`, gets a question and no card; the TEE policy stays the real wall), `freeze-advisor` (#185: reads only, points to "Freeze wallet"; no freeze tool exists, by design), `split-bill` (#177) and `revenue-split` (#190: split kept in working memory) send one `send_payment` per person, each with its own approval, `treasury-report` (#189) and `spending-audit` (#184) only read `get_balance` / `list_payments`. Refused payments are visible: the backend stores every attempt and `list_payments` returns `policy_denied` / `wallet_frozen` rows with their `message`. Incoming transfers are not listed by any tool (only the balance shows them), and Autopilot runs get no wallet token, so a scheduled daily or weekly report cannot read the wallet yet; no Builder template was added.
- **Best price buyer (#176, `get_quotes`, skill `best-price`):** `get_quotes` reads the shop's `?quotes=1` (every seller, cheapest first, `onYourList` from the wallet's own policy) and adds `cheapestOnYourList`; `buy_data` takes an optional `seller` id. The skill shows the comparison and buys only the cheapest seller with `onYourList: true`. Sellers come from the backend's `SHOP_SELLERS` (intended `lin1er.testnet:1.0,testing7.testnet:0.8`, not set yet). Never call it NEAR Intents.
- **Price watch (#179, skill `price-watch`):** `get_quotes`, then `add_numbers` (limit minus price) decides; buys through the same `buy_data` + `send_payment` approval only at or under the owner's limit. Autopilot runs drop `send_payment`, so there it only checks and reports. No Builder canvas template exists in the repo yet, so none was added.
- **Invoice & get paid (#180, `near_check_transfer`, skill `invoice`):** `list_payments` only lists what the Mind sent and `get_balance` does not say who paid, so "paid" needs `near_check_transfer` (RPC `tx` by hash + sender: success, receiver, NEAR moved). The tool itself sets `toThisMindsWallet` (receiver vs the wallet's own address from `/internal/v1/wallet/balance`) and `coversAmount` (vs the required `amountNear`, in yocto; it was optional and the model once left it out): in a live test (11 Nov) the model read two equal 64-character addresses as different and called a real payment unpaid. It reads `NEAR_RPC_URL` per call. The invoice goes out with `mail_send` (approval), so the `email-address` skill must be on too. The skill has no `send_payment`.
- **Mind as seller (#181, `sell_offer`, `buy_from_mind`, skill `mind-seller`):** `sell_offer` (approval) publishes through `PUT /internal/v1/offers/{item}`, paid into the Mind's own wallet; `buy_from_mind` is the 402 pattern against `GET /internal/v1/minds/{sellerMindId}/offers/{item}`. The buyer's wallet must list the seller's address or the policy refuses the payment before signing. Try-out Minds can neither sell nor be bought from.
- **Email tools (#13, #43, `src/email.ts`):** `gmail_list_emails`, `gmail_read_email`, `gmail_create_draft` (no send tool; drafts only), and `gmail_organize` (#106 step 2: archive or label up to 20 emails in one approval; archive removes `INBOX`, nothing is ever deleted; `GMAIL_CREATE_LABEL` finds or makes the label, then `GMAIL_ADD_LABEL_TO_EMAIL` per email, failures listed; with `demo` it changes nothing and its `note` makes the Mind say so). A run with `demo: true` (judge try-out user) reads `SAMPLE_INBOX`, fictional and fixed, with times relative to now; results carry `source: "sample_inbox"`. Without `demo` they read the run user's own Gmail through Composio (`src/composio.ts`, REST v3.1): one tool-router session per user id (cached 30 min, reopened once on 404), then `execute` of `GMAIL_FETCH_EMAILS` / `GMAIL_FETCH_MESSAGE_BY_MESSAGE_ID` / `GMAIL_CREATE_EMAIL_DRAFT`. The Composio user id is the backend user id (`USER_KEY` in `RequestContext`), so a session only reaches that user's Gmail. No connection (`400 ToolRouterV2_NoActiveConnection`), no user or no `COMPOSIO_API_KEY` → "Gmail is not connected". Never log the session response (it carries MCP connection headers). Owners must never get the sample. The sample keeps one email that tries to instruct the Mind: the `email-triage` playbook must flag it. App tools are named `<app>_<action>` so the Mind Graph maps them to `app:<app>`. `email-triage` is `available`; no catalog skill is `blocked` right now, so tests add a temporary one.
- **Mail and privacy skills (#183 to #193, live tests in `test/skills-mail.test.ts`):** `phishing-detector` (flags money/key requests and instructions aimed at the AI, labels with `gmail_organize` after approval, never acts on them); `confidential-reader` (dates, amounts, obligations of a sensitive email; the privacy claim is verified TEE inference only, never encrypted storage); `redact-before-send` (the model removes personal data before `mail_send` / `http_request` and lists it; not a separate filter); `health-journal` (log in working memory via Mastra's `updateWorkingMemory`, no medical advice) and `spending-tracker` (Gmail receipts by category), split because the log needs no Gmail; `follow-ups` (people who owe the owner, Gmail drafts only, no `mail_send`); bills and due dates extend `subscriptions` (title "Subscriptions & bills", #193) instead of a second skill over the same emails. Sample inbox `demo-9` to `demo-15` exist for them (a recovery-phrase phish with no payment address, a contract, an overdue invoice promise, an unanswered quote, a bill due in 6 days, two receipts); the default list shows the newest 10.
- **Mail tools (#96, `src/mail.ts`):** the Mind's own AgentMail address, in the `email-address` skill (in no template: the backend creates an inbox when the owner equips it, and the Free plan has 3 inboxes). `mail_send` (`requireApproval`, so never in workflows/Autopilot), `mail_list`, `mail_read` call the backend's `/internal/v1/mail/*` with `X-Engine-Key` and the run's `mailToken` (`X-Mail-Token`), exactly like the payment tools: token in `RequestContext` as a `Map` (`MAIL_KEY`), in `hiddenValues`, no token → "no email address yet" without calling the backend. `mail_send` passes the tool call id as `idempotencyKey`. A `rejected` / `rate_limited` send becomes a `tool.error` with that status (`isMailRefusal`). Read results carry `warnings` (Agent Armor `review`/`unavailable`, `spam`/`unauthenticated` labels): the playbook flags them and never acts on mail content. Graph node `app:mail`. `test/engine.test.ts` does not check the mail token yet (not proven yet).
- **Calendar tools (#57, `src/calendar.ts`):** `googlecalendar_list_events`, `googlecalendar_create_event` and `googlecalendar_create_meeting` (both `requireApproval`), in the `daily-planner` skill. One Composio session per user enables `gmail`, `googlecalendar` and `googlemeet` (`composioTool(context, app, slug, args)`); a toolkit the user has not connected answers `NoActiveConnection` for that app only (checked live 7 Nov for googlecalendar) → "Google Calendar is not connected" / "Google Meet is not connected". Composio slugs `GOOGLECALENDAR_EVENTS_LIST` (`calendarId: "primary"`, `singleEvents`, `orderBy: "startTime"`, `data.items`) and `GOOGLECALENDAR_CREATE_EVENT` (`data.response_data`, `data.display_url`). **`GOOGLECALENDAR_CREATE_EVENT` has no end time** (schema read live 9 Nov): send `composioTiming(start, end)`, i.e. `start_datetime` naive in UTC + `timezone: "UTC"` + `event_duration_hour` (0–24) / `event_duration_minutes` (0–59, default 30), so events are 1 min to 24 h. `send_updates` is a boolean. Always `create_meeting_room: false` (it needs a paid Workspace account). Times from the model must carry an offset (`ISO_WITH_OFFSET`). `googlecalendar_create_event` never passes attendees and sends `send_updates: false`: nobody else is emailed. Demo runs read `SAMPLE_CALENDAR` (relative to today, UTC; one invite tries to instruct the Mind) and never call Composio.
- **Meetings and Meet links (#97, option 2):** `googlecalendar_create_meeting` is its own tool because it emails other people in the owner's name; its approval `args` always carry `attendees` (emails, ≤ 20, checked again by `checkAttendees`) and `meet` (required, no defaults: Mastra's approval `args` are the model's raw arguments). Mastra answers a schema failure with `{ error: true, message }` instead of throwing. Flow: `GOOGLEMEET_CREATE_MEET` (`access_type: "TRUSTED"`) → `data.response_data.meetingUri` (field name from Google's Meet REST API; Composio's output schema does not list it, not seen live yet) → `GOOGLECALENDAR_CREATE_EVENT` with the link in `location` (if the owner gave none) and `description`, `attendees`, and `send_updates: true` only when there are attendees. The description and the `daily-planner` playbook say guest addresses come only from what the owner typed, never from an email or tool result. Demo runs return `SAMPLE_MEET_LINK` (`meet.example`, never a real Meet code), `invitesSent: false`, no Composio call.
- **Business apps (#194, `src/apps.ts`):** Sheets, Drive, Docs, Slack, Notion, Outlook (#195-#200), one small skill each (`sheets`, `docs`, `slack`, `notion`, `outlook`): an owner equips only apps they connected, and existing skills never gain a connection. The Composio session enables the backend's eleven `TOOLKITS` (`discord`, `hubspot` have no engine tools yet). Every call goes through `appCall`: try-out runs throw "not available in the try-out" without calling Composio (no sample data for these apps); `NoActiveConnection` → "<App> is not connected". Writes use `requireApproval`: `googlesheets_append_row`, `googledocs_create_document`, `slack_send_message`, `notion_create_page`, `notion_add_row`. Outlook mirrors the Gmail tools' shapes and is drafts only (`outlook_create_draft`, no approval, like `gmail_create_draft`). **Slugs and schemas read live 11 Nov 2026 with `?version=latest`** (the plain `GET /api/v3/tools?toolkit_slug=` list returned stale slugs for Outlook, e.g. `OUTLOOK_OUTLOOK_LIST_MESSAGES`, which 404s at latest): `GOOGLESHEETS_SEARCH_SPREADSHEETS` (`query`, `search_type` name/content/both, `max_results` → `spreadsheets[]`), `GOOGLESHEETS_BATCH_GET` (`spreadsheet_id`, `ranges[]` → `valueRanges[]`), `GOOGLESHEETS_SPREADSHEETS_VALUES_APPEND` (camelCase `spreadsheetId`, `range`, `valueInputOption` sent `RAW` so formula-looking text stays text, `values` 2-D → `updates.updatedRange`); `GOOGLEDRIVE_FIND_FILE` (`q`, bare text = fullText; `pageSize` → `files[]`); `GOOGLEDOCS_GET_DOCUMENT_BY_ID` (`id` or URL → Docs `body.content`, text from `textRun.content`); `GOOGLEDOCS_CREATE_DOCUMENT_MARKDOWN` (`title`, `markdown_text` → `documentId`, `display_url`); `SLACK_LIST_ALL_CHANNELS` (`limit` **defaults to 1**, always sent; `types`, `exclude_archived` → `channels[]`); `SLACK_SEND_MESSAGE` (`channel` without `#`, `markdown_text` → `ok`, `channel`, `ts`; `ok: false` + `error` is a refusal); `NOTION_SEARCH_NOTION_PAGE` (`query`, `filter_value` page/database, `page_size` → `results[]`), `NOTION_FETCH_BLOCK_CONTENTS` (`block_id` → blocks, text in `<type>.rich_text[].plain_text`), `NOTION_CREATE_NOTION_PAGE` (`parent_id`, `title`, `markdown`), `NOTION_INSERT_ROW_DATABASE` (`database_id`, `properties: [{ name, type, value }]`, values strings; we allow only writable types); `OUTLOOK_LIST_MESSAGES` (`folder`, `top`, Graph `search` → `value[]`), `OUTLOOK_GET_MESSAGE` (`message_id`), `OUTLOOK_CREATE_DRAFT_REPLY` (`message_id`, `comment`). Answers follow the output schemas; **none seen live** (no account connected; a human must connect a test account). Discord's toolkit has 28 tools at latest (`GET /api/v3/tools?toolkit_slug=discord&toolkit_versions=latest`; user-scope reads such as `DISCORD_LIST_MY_GUILDS`, `DISCORD_GET_MY_USER`) and none that posts a message, so #198 posting needs a bot toolkit; not wired. Graph: `app:<toolkit>`. Live tests: `test/skills-connections.test.ts` (try-out only).
- **Calendar conflict check (#192, skill `calendar-conflicts`):** `get_time` + `googlecalendar_list_events` once, reports overlaps and zero-gap pairs, suggests moves, changes nothing (`googlecalendar_create_event` only for a buffer the owner asks for). `SAMPLE_CALENDAR` has one overlap (`demo-cal-7` inside `demo-cal-3`) and one back-to-back pair (`demo-cal-4` → `demo-cal-8`).
- **Thread titles (#86, `src/titles.ts`):** on a thread's first run (no Mastra thread with that id yet), `makeTitle` asks `config.titleModel` (`z-ai/glm-5.3-flash`, the cheapest Confidential TEE chat model, through the same verified transport) for a 3 to 6 word title of the first message. It starts *before* the run, so it is usually ready when the run ends, and is sent as `thread.titled` `{ threadId, title }` after `run.finished` and before `run.verified`. It never throws: a failure or the 30 s limit means no event, and the backend keeps the first-message cut. GLM sometimes reasons ~300 tokens on a one-word message (26 s measured for "tes" on 9 Nov), so keep `titleMaxOutputTokens` and `titleTimeoutMs` generous. The title call is not part of the run's verification.
- **House style (`src/mind.ts` `WRITING_STYLE_RULE`):** every Mind's system prompt says never to use em or en dashes (a comma, colon, full stop or parentheses instead; ranges with "to" or a hyphen). Measured 9 Nov: 16 em + 12 en dashes in 5 replies before, 0 after. Keep new playbooks and templates free of them too, or the model copies them.
- **Greetings and language (#205, `src/mind.ts` `SMALL_TALK_RULE`, `LANGUAGE_RULE`):** greetings, thanks and small talk get a short reply with no tool calls (Mastra's own injected text says to activate a matching skill "immediately" and update working memory "proactively": a "halo" once ran 4 steps in 37 s); replies follow the owner's language with standard spelling (KBBI for Indonesian). No temperature is set anywhere in the engine (provider default). Measure with `node --env-file=.env --import tsx scripts/measure-greetings.mts [--runs 3] [--engine <other checkout>/engine] [--json out.json]` (live NEAR AI); live effect not proven yet.
- **Attack Playground (#16, `src/attacks.ts`):** four fixed scenarios (`GET /v1/attacks`); a run with `attackId` ends with `attack.verdict` naming the layer that stopped it (`model`, `no_tool`, `approval`, `policy`, or `none` if a payment went out). Measured 9 Nov with GLM low reasoning on try-out data, 3 runs each: direct order refused by the model 3/3; email injection refused 2/3 and once a card for the real Lumen invoice (not the attacker, `attackerTargeted: false`); rogue skill `no_tool` 3/3; tricked owner refused 2/3 and once a card to the attacker, which the policy refuses after approval. So the policy layer only shows when the model or the owner is fooled: the demo's "approve anyway" step is what makes `policy_denied` visible. Never claim a tx for a refused payment.
- **Time (#112, `get_time`, `localTime` in `src/tools.ts`):** runs may carry the owner's IANA `timeZone` (from the browser via the backend; checked again with `Intl`). It sits in the request context (`TIME_ZONE_KEY`), and `get_time` returns UTC plus the local `date`, `time`, `weekday` and `utcOffset`. Never let the model work out a weekday: it called Monday 9 Nov 2026 a Sunday. Without a zone everything is UTC. Autopilot runs use the schedule's time zone (stored in the schedule's `requestContext`, #146).
- **Calendar times in the owner's zone (#214, `localTimes` / `withLocalTimes` in `src/calendar.ts`):** every event a calendar tool returns (sample and Composio lists, and what `googlecalendar_create_event`, `googlecalendar_create_meeting` and `googlecalendar_block_time` echo back) carries `startLocal`, `endLocal` (e.g. `"Wed 11 Nov 17:00"`) and `timeZone` from the run's `TIME_ZONE_KEY` (UTC without one), next to the raw ISO `start`/`end`. All-day events read `"Tue 10 Nov, all day"` in every zone, `endLocal` the last day (Google's end date is exclusive). The calendar playbooks show those values as given and never convert by hand; anything not on the calendar goes under **Suggestions**, never listed as an event. Before this the model showed the 10:00 UTC sample standup as 10:00 WIB in 2 of 3 runs and once listed made-up events. Live test: `test/calendar-local-times.test.ts` (3 runs, Asia/Jakarta); not run yet.
- **Memory per persona version (#116, `resourceId` in `src/mind.ts`):** memory is `userId:mindId`, or `userId:mindId:v{n}` once the backend sends `mind.personaVersion` (bumped when the owner changes the name or soul). A renamed Mind once signed with its old name, recalled from resource-scoped memory. Old memory stays in the database but is no longer read; skills or model changes keep the memory.
- **Deleting a chat (#207, `src/threads.ts`, `DELETE /v1/minds/{mindId}/threads/{threadId}` with `{ userId }`):** `forgetThread` checks the thread's resource is the caller's (`ownsResource`: `userId:mindId` or `:v{n}`, else `404`), then `Memory.deleteThread` (from `mindAgent.getMemory()`: a bare `Memory` has no storage until the agent hands it Mastra's) and `await memory.settled()`. `PostgresStore.deleteThread` removes the messages, the `memory_messages*` vector rows (today `mastra.memory_messages_1024`) and the thread in one transaction, so a deleted chat no longer comes back through resource-scoped semantic recall. A missing thread is `204` (the backend retries until `204`). Working memory is per resource and stays. `test/threads.test.ts` writes rows and fake vectors directly (no NEAR AI); its last test embeds through NEAR AI and checks real recall.
- **HelloNear guide and the Mind's own skills (#114):** `skills/hellonear-guide` has `builtin: true`: every Mind loads it (`mindSkills` in `src/skills.ts`), it is left out of `GET /v1/skills`, and it can't be equipped. It holds only what the app really has (screens, buttons, skills, try-out rules, "HelloNear support" messages are phishing); keep it in step with the FE when screens change. Each SKILL.md also has `title` (the Skills screen name) and `blurb` (one line on what it can and cannot do): `skillsLine` in `src/mind.ts` puts the Mind's skills and the ones it could add into its prompt. Without blurbs it once told an owner to add Email helper to send email, which Email helper cannot do.
- **Memory in Settings (#209, `src/memory.ts`, `GET`/`PUT`/`DELETE /v1/minds/{mindId}/memory`):** the owner reads, replaces and clears the working memory of one resource, `resourceId(userId, mindId, personaVersion)`, the key chat runs use (GET takes `userId` and `personaVersion` as query parameters; PUT `{ userId, personaVersion?, markdown }` (at most 20,000 characters) answers `{ memory: { markdown, updatedAt } }`; DELETE `{ userId, personaVersion? }` answers `204`). Working memory is **free Markdown**: `mastra.ts` sets no `template` or `schema`, so the Mind is only shown Mastra's default template ("# User Information" with bullet fields) and each `updateWorkingMemory` replaces the whole document (docs-memory-working-memory.md in `@mastra/memory`). `updatedAt` is the row's (`mastra.mastra_resources`), one time for the whole document; nothing stamps sections. Clearing writes `''`, which `Memory.getWorkingMemory` reads as none; recall embeddings of past chats stay (deleting a chat drops those, #207). **Switches per run:** `mind.memory: { enabled?, recall? }` (absent = on); `memoryOptions` turns `false` into Mastra per-call `memory.options` (`workingMemory: { enabled: false }`: no document in the prompt, no `updateWorkingMemory` tool; `semanticRecall: false`: no vector search and the run's messages are not embedded, so chats held with recall off are not found later either). Workflow and Autopilot agent steps take no per-call options and keep the defaults. Tests: `test/mind.test.ts` (unit) and `test/memory.test.ts` (Postgres; the switch tests run the real Memory on Mastra's mock model and check its prompt and tools; one test embeds through NEAR AI).
- **Stop (#121, `abortOnClose` in `src/server.ts`):** chat and approve/decline runs pass an `abortSignal` to Mastra that fires when the backend drops the request (its cancel route aborts the fetch). Measured 9 Nov: without it the engine kept writing ~25 s (301 text deltas) after the cut, so the model kept spending tokens; with it, 0. The wallet and mail tools call the backend without that signal, so a payment already sent to OutLayer is never cut halfway. Builder workflow runs are not covered yet.
- **#124 (live Meet test):** `meetLinkOf` takes the first `https://meet.google.com/` URL anywhere in Composio's answer (live, it was not at `response_data.meetingUri`); without one the error lists the field names it saw, never values. With a run `timeZone`, the prompt states the owner's zone and offset (`timeZoneLine`), and the calendar create tools refuse a time whose offset is not the owner's at that moment (`checkOwnerOffset`): "tomorrow 2pm" once became 14:00+00:00. Reply text goes through `plainDashes` (em and en dash → hyphen), because the prompt rule alone still let them through from real calendars; display only, verification covers the model's bytes.
- **Composio tool versions (#124):** the tool router runs each tool's **latest** version, not the default schema `GET /api/v3/tools/{slug}` shows. Always read `?version=latest` before changing tool arguments. On 9 Nov `GOOGLECALENDAR_CREATE_EVENT` latest (`20261103_00`) takes `start_datetime` / `end_datetime` with an offset (end wins over the duration fields) and `send_updates: 'all' | 'externalOnly' | 'none'`; a boolean failed live. `create_meeting_room` now defaults to true there, so it is always sent `false`.
- Emit stream events in the shape agreed in `docs/api-contract.md` (#7); the Mind Graph depends on them.
- In stream chunks, `payload.toolName` is the **key** in the agent's `tools` object, not the tool's `id`. Use the same string for both to avoid mismatches.
- **Skills** live in `skills/<name>/SKILL.md` (YAML frontmatter: `name` = folder, `description`, `metadata.hellonear.{tools, connections, status, note?}`). `tools` must be keys of `toolRegistry` in `src/tools.ts`; `status` is `available`, `simulated` (works but fakes a side effect, say how in `note`) or `blocked` (never loaded). The loader fails fast on any mistake. **Shared references:** a skill can list files under `metadata.hellonear.references` (e.g. `[near-recipients.md]`); the loader reads them from `references/` (engine root) and passes them to `createSkill({ references })`. The Mind opens one with `skill_read` (path `references/<file>`) only when its playbook says so, so the text stays out of every prompt (#123) and several skills share it (Payments and NEAR account lookup both use `near-recipients.md`). Write references from live docs and say which page and date; keep them short. Proven 9 Nov in Chrome against a local stack (fake OutLayer with a 0.1 NEAR limit and whitelist): Payments looked up the recipient before the approval card; `lumenhost.testnet` (does not exist) was refused with no card; a 64-character implicit id that was never used made it call `skill_read` for `near-recipients.md`, warn, and ask before paying; an approved 0.01 NEAR to `alice.testnet` came back sent; 0.5 NEAR showed "blocked even if you approve" with no Approve button.
- **Templates** live in `templates/<templateId>.json` and may only use skills from the catalog. Keep guardrails (`soul.invariants`) in every template. Each template has a `quote` (≤ 80 characters, the card line in the Mind's own voice) and a character voice in `soul.identity`; money facts (amount, recipient, owner's approval) stay plain, never jokes about refusals or limits (#55). Since 11 Nov each starts with the skills its tracks show (#194): Payments Mind adds recipient-guard, split-bill, treasury-report, spending-audit, best-price, freeze-advisor; Email Manager adds phishing-detector, follow-ups, subscriptions, confidential-reader, calendar-conflicts; General Assistant adds calendar-conflicts, health-journal, redact-before-send (`test/templates.test.ts`). Only Minds made after that get them; existing Minds keep their list.
- Never let the backend choose tools: it sends skill ids, the catalog maps them to tools. `GET /v1/skills` publishes the catalog (every skill, its status and tools); keep it the one list the backend validates against. Its items also carry `title` and `blurb`; `GET /v1/skills/{skillId}` returns one equippable skill with `markdown`, the SKILL.md body without frontmatter (`skillDetail` in `src/skills.ts`, 404 for unknown and built-in skills, no references) (#220).
- **Visual Builder (#20, `src/builder.ts`, `src/workflows.ts`):** canvases compile to Mastra dynamic workflows (Beta). Rules from spike 02, keep them: never allow a `requireApproval` tool as a workflow step (Mastra runs it without asking); workflow runs set `UNATTENDED_KEY` so agent steps never see approval tools; never let user text reach a Mastra `${...}` template (templates can read `requestContext`, which holds the secrets), so the compiler only emits templates it built from `{{steps.…}}` / `{{input.…}}`; mappings are top-level only, so condition branches share one mapping. **If ways of several steps (#153):** a way with two or more steps compiles to its own dynamic workflow (`wayWorkflowId`: `<parent id>--then|else`) referenced from the `conditional` as `{ type: 'workflow' }`; values from before the If reach it through the shared mapping as `<handle>_pN` inputs. Children are registered before the parent, kept out of `listWorkflows` (no `metadata.hellonear`), removed when a way shrinks back to one step and deleted with the job; Mastra reloads them on boot (checked after a restart). Its steps stream as `way-<handle>.<node>` (the `steps` map has those keys; the way's own entry has `way: true`, is skipped by the normalizer and gives run history the way's final output, the only part Mastra snapshots). `requestContext` reaches the steps inside (spike on #153). One-step ways compile as before. **Ifs anywhere and End (#164, `compileTree` in `src/builder.ts`):** canvases with an `end` node, more than one If, or an If with a plain (no `sourceHandle`) edge compile as a tree; the old shapes keep the old compiler, so saved jobs don't change. Every way and every "after the If" is a nested dynamic workflow (`<job id>--<if id>.then|else|next`), because a mapping must never read a step that didn't run (spike on #164: `Invalid path … in step b`). Values from earlier on the path reach a nested workflow through its parent's mapping as `<prefix>pN` inputs, recursively. A nested block that carries on ends with an `out` mapping `{ continues: true, s_<node>: <output> }`; one that hits End writes `continues: false`; one that ends with an If returns that If's output (`{ <way step id>: … }`). The steps after an If run behind a conditional on `or(truthy stepResults.<way>….continues)`, which is missing (false) for a way that ended. Each nested workflow declares its output schema, or Mastra's validator refuses the predicate paths. Steps stream as `<if>:<handle>.…<node>`; run history (`listRuns`) reads `s_<node>` from nested outputs and orders them by `steps[…].order`, since Postgres reorders JSON keys. Children are deleted by id prefix when no longer used. Tools must be registered on the `Mastra` instance (`tools`) to be usable in workflows. **Canvas-only tools (#146, `CANVAS_ONLY` in `src/tools.ts`):** `mail_send_to_owner` (Email me) and `googlecalendar_block_time` (Add to my calendar, today at a time of day in the owner's zone, no guests) run without asking only as steps the owner puts on a canvas: the registry's versions have no `requireApproval`, because the owner placing them is the approval, and `toolsFor` never offers them to the model. **Email me in a chat (#205):** a chat run (not unattended) gets `mailSendToOwnerInChat` under the same key `mail_send_to_owner` (`IN_CHAT` in `src/tools.ts`), same input and backend call but `requireApproval: true`, so "email me the link" shows an approval card instead of the Mind asking for the owner's address; workflows and Autopilot still get neither version, `needsApproval('mail_send_to_owner')` stays false so the Builder accepts the step, and `missingTools` is unchanged. The `email-address` playbook says to use it for "email me" / "kirim ke emailku" and never ask for the address. `googlecalendar_block_time` has no chat version. Live tests: `test/skills-mail-owner.test.ts` (fake backend). Keep them to the owner's own things. `mail_send_to_owner` never takes a recipient (the backend sends to the owner's Gmail address) and the compiler refuses references in it to anything but an agent step's note, so raw email or web text is never forwarded. Call `mastra.startWorkers()` at boot or saved workflows are not loaded. Agent run limits live in the agent's `defaultOptions` because workflow agent steps take no per-call options.
- Each workflow run stores a Mastra snapshot (~8 KB, measured: 5,000 runs ≈ 39 MB in `mastra_workflow_snapshot`), including its `requestContext`. Secrets stay out only because they are a `Map` (serializes to `{}`); keep them a `Map`, and `test/workflows.test.ts` scans every `mastra` table for the secret. Retention: `storage` declares `maxAge` (`RUN_RETENTION_DAYS`) and the server calls `storage.prune()` hourly; Mastra never prunes by itself.
- **Autopilot (#21, `src/autopilot.ts`, spike 03):** one Mastra workflow schedule per builder workflow, created with `mastra.schedules.create({ workflowId, requestContext: { mind, unattended: true, userId, mindId, timeZone }, resourceId: userId })`. The ids and the zone are not secrets: `userId` opens the owner's Composio session (calendar and inbox steps had none before #146), `mindId` reaches Email me. A schedule's `requestContext` is stored as plain JSON, so **never put secrets in it**; canvases with `{{secrets.…}}` are refused until the backend can hand secrets to unattended runs. The Mind config is a copy: anything that makes a schedule invalid pauses it with `pausedFor` instead of letting it run old config. Always set a timezone (we default to `UTC`). Run history comes from run snapshots (`listWorkflowRuns`), not trigger rows. The scheduler only ticks after `mastra.startWorkers()`. Scheduled runs have no live stream, so no badge.
- Spikes live in `spikes/<nn>-<name>/` with a README stating the result, how to run it, and what it does not cover.

## Commands

- Package manager: **Bun** (`bun install`, lockfile `bun.lock`, version pinned in `packageManager`). The scripts still run on **Node** (`node --import tsx …`): the NEAR AI SDK requires Node ≥ 24.22.1 and the tests use `node:test`; running the engine on the Bun runtime is not tested. Do not add `package-lock.json` back.
- `bun run dev` (port 4100), `bun run test:unit` (offline), `bun run test` (unit + integration: real NEAR AI, local Postgres, NEAR testnet RPC, httpbin), `bun run typecheck`.
- Postgres: `docker compose up -d postgres` from the repo root; `docker compose stop` when done.
- Load tests: `load/chat.js` (spends NEAR AI credit, keep it small) and `load/workflow.js` (builder; local tools only by default, `-e AGENT=1` adds an agent step). Never load test a public endpoint (NEAR RPC, httpbin): docs.near.org forbids it for shared RPCs.
- Run `bun run test` and the load test before every push/merge that touches the engine, and report results in the PR.

## Testing notes

- LLM output varies. Assert on what the engine guarantees (events, seq, tool execution, approval gating), not on exact wording, and only on the tool under test (after a decline the model may call other tools).
- Tools needing approval require Mastra storage (snapshots); tests use the local Postgres.
- Changing a Mind's persona mid-thread: the instructions do change per request, but the model tends to copy its own earlier replies in that thread (verified 3 Nov). Start a new thread after a persona change, and test persona switches on a new thread.
